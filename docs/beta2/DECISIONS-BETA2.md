# β2.00 の確定判断

先生の要件から一意に決まらなかった論点について、現物を実査したうえで下した判断と、
その理由・却下した案を残す。**実装中にここを蒸し返さない。**
事実と食い違いが見つかった場合だけ、事実を示して改訂する。

---

## D-01 診断は「ひな形の 1 つ」ではなく「固定の段階」にする

**判断**: 第 1 段階の診断は必ず 1 回通る固定の段階とし、ユーザーに選ばせない。
文面は `presets/01_診断/` の**ちょうど 1 つ**のファイルが持ち、一覧は画面に出さない。

**理由**: 要件 A の「トップレベルで分岐させない」は、分岐を後ろへずらすだけでなく
**診断を素通りできなくする**ことで初めて成立する。診断を選択肢にすると
「診断しない」という選択肢が生まれ、入口の分岐が復活する。

**却下**: 「診断ひな形を複数置いて選ばせる」— 選択肢が増えるだけで、
選ぶ材料（＝診断結果）をまだ持っていない段階の判断を増やす。

**副作用の受容**: 有効ファイルが 0 件／2 件以上なら **E-PRESET-02** で止める。
β1.10 簡易モードの「並び順で最初のもの」方式は採らない。黙って選ぶのは
「不正形式を黙って受理しない」という β2 の規律に反する。

## D-02 想定動作環境は JSON にする（Markdown にしない）

**判断**: `environment/target-environment.json`（機械可読の正本）＋
`environment/SOURCES.md`（人が読む出典・改訂履歴）の 2 ファイル構成。

**理由**:
1. 制約に**安定した機械キー**が要る。診断契約の `META ... ENVKEY=` がそれを参照し、
   実在しないキーを拒否する（SPEC §4.5 D14）。この検査が「AI が環境を見ずに書いた」
   指摘を機械的に落とす。散文 Markdown ではキーを持てず、持たせるなら独自パーサが要る。
2. `pub/vba-devkit/config/analyze.json` に先例がある。同じ問題領域で同じ形が選ばれている。
3. `presets/*.md` が Markdown なのは**文面を AI へそのまま渡すから**であって、
   人が編集するからではない。環境定義は文面ではなく**構造化された事実**であり、
   渡す形（§3.6 の整形ブロック）は JSON から生成する。役割が違う。

**却下**: 「`presets` と同じく Markdown で書く」— 一貫性は上がるが、
上記 1 の検査が成立しなくなる。一貫性より検査可能性を取る。

**保守性の担保**: `SOURCES.md` が出典・軸の意味・改訂の書き方を日本語で持ち、
`E-ENV-01` のカードがどのフィールドが足りないかを名指しする。

## D-03 環境定義の初期値はすべて `declared` / `inferred` にする

**判断**: `basis: "observed"` を名乗る項目は初期状態で 0 件とする。

**理由**: 実測データがこの世に存在しない。`pub/datadesk/envtest/results/` は
`.gitignore` されて空であり、README と `AGENTS.md` が参照する `.repos/CONSTRAINTS.md` は
`C:\repos\pub` 配下の全再帰検索で 0 件だった（[AUDIT-BETA1.md](AUDIT-BETA1.md) §2.2.1）。
`pub/vba-devkit` の `Basis = 'observed'` は「検出パターンが検証で立った」の意味であり、
「対象端末でその制約が実測された」ではない。**混同すると、測っていない前提を
測ったものとして AI と利用者へ提示することになる。**

**帰結**: 画面には想定環境の名前と版を常時出すが、「実測済み」とは書かない。
将来 `datadesk/envtest` を対象端末で走らせた結果が入ったら、
該当項目を `observed` へ上げ、`sources[]` にその結果を足す。手順は `SOURCES.md` に書く。

## D-04 診断契約には「直し方を書く欄」を作らない

**判断**: 診断パッケージの構造に `REMEDY` / `FIX` / `PLAN` に相当するブロックを置かない。

**理由**: 要件 B の「この段階では改修方針・動作変更予測・『改修不要』等を決めない」を、
文章の指示ではなく**構造**で強制する。書く場所が無ければ、契約に従う限り書けない。
散文で頼むだけの規律は、返答が長くなるほど守られなくなる。

**副作用の受容**: AI が `TEXT BEGIN IMPACT` の中へ直し方を混ぜて書く余地は残る。
これは検査で落とせない。落とせないことを認めたうえで、
画面 3 が第二層に出すのは「成立条件 / 影響 / 該当箇所 / 根拠」というラベルであり、
そこに直し方が混ざっても**次の段階の入力欄が空である**という事実は変わらない。
希望動作を書くのは常に人である。

## D-05 `CONFIDENCE=UNVERIFIED` は `BLOCKER` / `DEFECT` を名乗れない

**判断**: SPEC §4.5 D11 として機械的に拒否する。

**理由**: 要件 B の「曖昧なものを断定しない」を検査可能な形へ落とす唯一の方法。
「確実に動かない」と「確認していない」を同時に名乗る指摘は、それ自体が矛盾している。

**同様に D12**: `CLASS=BLOCKER` は `ENVKEY` を必ず持つ。環境上の阻害要因を名乗るなら、
どの環境制約に当たるかを指させる。指せないなら `CONDITIONAL` である。

## D-06 決定的置換は「検出はするが判断はしない」で §1.2 と両立させる

**判断**: β1.10 §1.2 の「ツールは該当箇所を検出しない」を、
**字句的事実の検出は可、良し悪しの判断は不可**へ限定的に修正する（SPEC §1.1）。

**理由**: 要件 F が「VBA 内のパス候補を検出・集約・表示」を明示的に求めている。
これは §1.2 と衝突するので、衝突を隠さず、境界を引き直して明文化する。
引き直した境界は「`"C:\data\"` という文字列リテラルが 3 か所ある」（事実）と
「その固定パスは直すべきだ」（判断）の間である。新しい値を決めるのは常に人である。

**却下**: 「§1.2 に触れず、検出を『ひな形の機能』と呼んで通す」—
実装が何をしているかを名前で誤魔化すことになる。

## D-07 置換エンジンは JS に置き、正規表現ベースの既存資産を流用しない

**判断**: `assets/js/vba-lexer.js` に本物の字句解析器を新規実装する。
`pub/vba-devkit/lib/VBAToolkit.psm1` の検出正規表現は**流用しない**。

**理由**:
1. 既存資産は `(?mi)^[^''\r\n]*"[A-Z]:\\"` の形で、行頭からアポストロフィまでを
   「コメント以外」とみなす近似である。`"Don't"` のような文字列で誤爆し、
   `REM` コメントを避けられず、行継続 `_` で分断されたパス連結を追えない。
   **調査ツールとしては許容できるが、コードを書き換えるツールには足りない。**
2. 置換は「行のテキストへの文字列置換」ではなく「トークンのスパン差し替え」でなければ、
   コメントや変数名を巻き込まない保証が作れない。
3. 置き場所が JS なのは、差分計算（`diff.js`）とプレビューが JS にあり、
   `buildBook` が JS から最終コードを受け取る現行構造と一致するため。
   C# 側へ置くと、プレビューのためだけに IPC 往復が増える。

## D-08 `public-release/package/` は β1.10 snapshot のまま凍結する

**判断**: β2.00 開発中、`public-release/package/` を一切変更しない。β2 へ同期しない。

**理由**（現行構造を実査したうえで）:
1. それは git 追跡下の**静的コピー**（63 ファイル）で、公開済み GitHub Release
   `v1.1.0-beta.1` の ZIP 内容と一対一に対応している。同期すると、
   「public-release」と名乗るフォルダが**実際には公開されていない中身**を持つ。
2. `tests/test-p9-distribution.ps1` はこのフォルダを**検査対象として参照していない**。
   自分で repo ルートからコピーを作って検査する（`ProductRoot` は `testdata` 内であることを要求）。
   **したがって同期しないことでテストが落ちることはない。**
   - **訂正（codex-implementer の指摘で実読し直した）**: 参照はしないが、
     `test-p9-distribution.ps1:165-175` は repo ルートの中身を
     `.git` と `testdata` **以外すべて**コピーするため、
     `public-release/` も配布ステージへ**間接的にコピーされている**。
     当初「参照 0 件」とだけ書いたのは不正確だった。
   - 結論は変わらない（凍結する）。ただし WP-10 で、配布ステージから
     `public-release/` `docs/` `tests/` `_audit/` `.playwright-mcp/` を
     **明示的に除外**する。配布物の中に配布物の旧版が入れ子で入っている状態は、
     検査の意味を薄くするうえ、コピー時間も無駄である。
3. β2.00 は先生の実画面テスト前のローカル作業ツリーであり、
   配布物を名乗れる段階にない。配布物の生成は先生が公開を決めたときに行う。

**却下**: 「β2 dev へ同期して常に最新にする」— 上記 1 の理由で、
公開済み成果物の記録という唯一の役割を壊す。

## D-09 β1.10 の「相談」「簡易モード」は削除ではなく移設する

**判断**: 入口は消すが、機能価値は一本道の任意詳細として吸収する（SPEC §9.3）。

| 消すもの | 価値 | 移設先 |
|---|---|---|
| 「AIで相談する」入口 | 進め方を相談できる／何でも聞ける | 画面 1「ほかに気になっていること」＋ 画面 4「追加の要望」 |
| `presets/04`（新端末診断） | 環境前提と報告のさせ方 | 環境定義ファイル ＋ 診断ひな形 |
| 「簡易モードで始める」入口 | 決めることを最小限にして最後まで行ける | **一本道そのもの**が引き受ける。診断を読まずに画面 3 でひな形を選び、希望動作を 1 行書けば最短経路になる |

**簡易モードの扱いの補足（数え直した事実）**: β1.10 の簡易モードで人が操作する画面は
6 つ（book / request / handoff / intake / review / done）。
β2 の最短経路は 9 つ（book / 診断依頼 / 診断取り込み / ひな形 / 希望動作 /
改修依頼 / 改修取り込み / diff / 出力名）である。
**β2 の最短経路は β1.10 の簡易モードより長い。** 短くなったとは言わない。

それでも簡易モードを消す理由は「同じくらい速いから」ではなく、
**診断を必ず 1 回通すという要件 A の骨格と両立しないから**である。
診断を飛ばす経路を残せば、それは「診断する / しない」というトップレベルの分岐であり、
入口の分岐を後ろへずらした意味が消える。

速さの担保は経路を分けることではなく、**通る画面それぞれで決めることを減らす**ことで行う
（画面 0 の統合、質問の畳み込み、指摘一覧の既定表示、`INFO` の既定折りたたみ）。
診断を読まずに画面 3 でひな形を選び、希望動作を 1 行書いて進むことは可能であり、
それを `tests/test-shortest-path.js` で固定する。

## D-11 クリップボードに有界の再試行を入れる

**判断**: `Clipboard.SetText` / `GetText` を**最大 10 回呼び出す**
（＝待ちは最大 9 回・各 50ms・合計 450ms）。
**再試行するのは `HRESULT 0x800401D0`（`CLIPBRD_E_CANT_OPEN`）だけで、
それ以外の例外は 1 回目で即座に失敗させる。**
最終失敗は `E-GEN-03` / 新設 `E-GEN-04` として**事実のまま出す**（SPEC §8.5）。

例外を区別しない再試行は、本当の失敗を 450ms 遅らせるだけで何も救わない。

**理由**: codex-implementer の β1.10 実測で `test-flow-webview.ps1` が 3 回連続失敗し、
原因が `0x800401D0`（`CLIPBRD_E_CANT_OPEN`）の一時競合だったため。
β2 は受け渡しが 2 回（診断・改修）に増えるので、当たる機会も増える。

**却下**: 「試験のアサーションを緩める」「失敗を warning へ落とす」—
テストを緩めて緑にしないという要件 G に反する。再試行は**製品の耐性向上**であって、
試験の緩和ではない。再試行を尽くした失敗は試験も製品も失敗として扱う。

## D-14 450ms を超えるクリップボード競合が実在した — それでも上限は上げない

**事実（codex-implementer が WP-01 実装後に実測、2026-08-01）**:
`test-flow-webview.ps1` を連続実行したところ、run1 / run2 は PASS、
**run3 が 10 回の呼び出しを尽くして同じ `0x800401D0` で失敗**した。
失敗直後の `GetOpenClipboardWindow` は 0。
再試行ヘルパーは仕様どおり 9 回・450ms 待ってから失敗を表面化しており、
テストは緩められていない。

**これは D-11 の前提の一部を反証している。** 私は「450ms あれば一時競合は抜ける」と
暗黙に仮定していたが、**少なくとも連続実行の条件下ではそうならない**。

**判断: 製品の再試行上限は 450ms のまま変えない。**

理由:

1. **必要な長さの根拠が無い。** 1 秒へ延ばして通ったとしても、それは
   「今回の競合が 1 秒未満だった」という 1 例にすぎない。上限を測定なしに動かすのは、
   数字を大きくして不安を消しているだけである。
2. **上限を延ばす方向は、失敗の表面化を遅くするだけ。** 本当に相手が掴んでいる場合、
   利用者は 1 秒固まってから同じ失敗を見る。450ms で失敗を出して
   ［もう一度コピー］を押せるほうが速い。
3. **回復経路が既にある。** コピー失敗は `E-GEN-03` ＋［もう一度コピー］、
   取り込み失敗は `E-GEN-04` ＋「`Ctrl+V` でも貼り付けられます」。
   **`Ctrl+V` は `paste` イベント経由で OS のクリップボード API を通らない**ため、
   ボタン経路が競合で落ちても貼り付けは成立する（β1.10 §7.3 の二経路がここで効く）。
   つまり**競合が 450ms を超えても製品は正しく壊れる**。黙って失敗しないし、行き止まりにもならない。
4. テストの上限を製品へ合わせて動かすのは、**製品を試験ハーネスの都合に合わせる**ことであり、
   向きが逆である。

**次にやること（推測で埋めない）**: 誰が掴んでいるのかを**測ってから**決める。

- 再試行の各回で `GetOpenClipboardWindow()` を取り、0 でなければ
  `GetWindowThreadProcessId` からプロセス名と PID を得る。
- 最終失敗時に WARN で「どのプロセスが掴んでいたか」をログへ残す。
  これは試験のためだけの計測ではなく、**利用者にとっても有用な事実**である
  （「別のアプリがクリップボードを使っています」は行動できる情報）。
- そのうえで、掴んでいたのが**直前の試験プロセス（WebView2 / WPF の終了処理）**であれば
  ハーネスの分離不足であり、`test-flow-webview.ps1` 側で
  **前のプロセスの完全終了を待ってから次を起動する**（これは試験の緩和ではなく、
  試験が自分で作った競合を取り除く**ハーネスの正しさの修正**である）。
- 掴んでいたのが無関係な常駐アプリであれば、それは環境の事実であり、
  製品は上記 3 のとおり正しく振る舞っている。**gate の解釈を変える**（下記）。

**gate の再定義**: 「`test-flow-webview.ps1` を 3 回連続で 3/3 PASS」の
「連続」とは、**前のプロセスが完全に終了してから次を fresh process で起動すること**を指す。
プロセスの終了処理と次の起動を重ねた状態は、製品が想定していない条件であり、
そこでの失敗を製品の欠陥として数えない。**ただし数えないだけで、記録からは消さない。**

**測定結果（2026-08-01、codex-implementer）**: 占有者は 10 サンプルすべて
`svchost pid=11820`、read-only 照合で service は `cbdhsvc_*`
（**Windows Clipboard User Service**）だった。**直前の試験プロセスではない。**

したがって上の分岐は「**無関係な常駐サービス**」側で確定し、
ハーネスの分離不足ではなく**環境の事実**である。上限は変えない。

**機序（これが分かったことの意味）**: `cbdhsvc` はクリップボード履歴（Win+V）と
クラウドクリップボードの担当で、**こちらが `SetText` した直後に、履歴へ取り込むために
クリップボードを開きに来る**。つまり競合は偶発的な外乱ではなく、
**こちらの書き込みが誘発している**。

β2 は受け渡しが 2 往復（診断・改修）あり、各往復で「書く → しばらくして読む」が起きる。
よってこの競合は珍しい事象ではなく、**クリップボード履歴が有効な Windows 10/11 では
通常運用で起こりうる**と考えるべきである。

これは上限を延ばす理由にはならない。相手は OS のサービスであり、
こちらが待てば必ず空くという保証は無い。**回復導線（［もう一度コピー］／`Ctrl+V`）で
受けるという設計が正しい**ことを、この機序が裏づけている。

**記録に残す**: この単発失敗は最終的な試験履歴に残す（SPEC §12 の未検証事項に追記）。
「3/3 になったから無かったことにする」はしない。

## D-13 `## 改修指示` の見出し名は変えない（診断ひな形でも同じ名前を使う）

**判断**: 診断ひな形でも、AI へ渡す本文の見出しは `## 改修指示` のままにする。
`## 依頼内容` への改称も、2 つの名前の併存も採らない。

**理由**:
1. この節は「`{{REQUEST_TEXT}}` になる本文」という役割で定義されており、
   段階（診断／改修）とは独立している。役割は変わっていない。
2. 改称すると `preset-document.js` の定数・エラーメッセージ 8 本・
   同梱ひな形 5 ファイル・`test-preset-document.js` / `test-preset-migration.js` /
   `test-prompt-template.js` が連動して動く。**機能上の利得はゼロ**である。
3. 2 つの名前を併存させるのは最も悪い。「どちらを書けばよいか」という
   新しい迷いどころを、ユーザーが編集するファイルの中に作る。

**副作用の受容**: 診断ひな形を編集する人は「改修指示」という見出しの下に
監査の依頼文を書くことになる。違和感は残る。
そのため `presets/01_診断/01_動作環境の事実監査.md` の先頭コメントに
「この見出しは AI へ渡す依頼文の本文という意味です」の 1 行を置く
（コメントは依頼文に入らない。β1.10 §5.2.1）。
