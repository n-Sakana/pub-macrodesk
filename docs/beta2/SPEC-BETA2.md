## 1. 目的と、この版で変える 1 点

β1.10 は「判断は AI、ツールは配管」という思想で完成している。その配管は正しい。
**問題は入口である。** 使う人はまず「AIで改修する / AIで相談する / 簡易モードで始める」の
3 択を、まだ何も見ていない段階で迫られる。自分のマクロに何が起きているか分からない人には
選べない選択であり、選び間違えると別の道へ入る。

β2.00 が変えるのは 1 点だけである。

> **何をするかは、マクロを見てから決める。**

そのために、読み込んだ直後に**事実監査**を 1 回挟み、その結果を見てから改修内容を決める
一本道にする。分岐は無くなるのではなく、**分岐の位置が「最初」から「診断の後」へ動く**。

### 1.1 中核思想の継続と、1 か所の限定的な修正

β1.10 §1.2「ツールは判断を持たない」は継続する。ただし決定的置換エンジン（§7）のために
**1 か所だけ限定的に修正する**。

| β1.10 §1.2 の記述 | β2 での扱い |
|---|---|
| 「どこが改修対象か・どう直すかの判断はチャット AI がやる。ツールは該当箇所を検出しない」 | **修正**: ツールは VBA の**字句的事実**（文字列リテラルがどこにあり、その値が何か）を検出してよい。ただし「それが誤りである」「こう直すべきだ」は依然として言わない |
| 「返答テキストからモジュール名・コードブロックを抽出する（＝意味の解釈）は禁止」 | **継続**。返答は自分で名乗った区切り行だけを信じる。推定しない |
| 「ひな形は検出ルールでもコード置換規則でもない」 | **継続**。ひな形は依頼の正本であり、置換規則はユーザーが入力する。ひな形は engine を指名するだけ |

区別の要点: **検出（detection）は事実の列挙、判断（judgment）は良し悪しの決定。**
「`"C:\data\"` という文字列リテラルが 3 か所ある」は事実である。
「その固定パスは直すべきだ」は判断であり、ツールは言わない。新しい値を決めるのは常に人である。

## 2. 一本道のフロー

### 2.1 進捗（4 手順）

```
① ブックを読み込む   ② 診断する   ③ 改修を決めて実行する   ④ ブックを作る
```

β1.10 の「用途で進捗バーが変わる」挙動は廃止する。**バーは常に 4 手順で固定**。
最初の画面から 4 段すべてが見えている（要件 E「必須データは最初から表示する」）。

### 2.2 画面表（全 11 画面）

`assets/js/screens.js` が唯一の正本であることは変えない。

| # | 名前 | 手順 | この画面で決めること | ［次へ］が有効になる条件 |
|---|---|---|---|---|
| 0 | `book` | ① | 対象ブック | ブックを読み込めた |
| 1 | `diagnoseRequest` | ② | 診断依頼の受け渡し | 依頼文をコピーし、フォルダも開いた |
| 2 | `diagnoseIntake` | ② | 診断結果の取り込み | 診断パッケージを受理できた（0 件の結論を含む） |
| 3 | `findings` | ③ | 診断結果の確認と、次にすること（ひな形 1 つ） | ひな形を 1 つ選んだ |
| 4 | `repairInput` | ③ | 対象と希望動作の入力 | §2.4 の経路別条件 |
| 5 | `repairRequest` | ③ | 改修依頼の受け渡し（**AI 経路のみ**） | 依頼文をコピーし、フォルダも開いた |
| 6 | `repairIntake` | ③ | 改修返答の取り込み（**AI 経路のみ**） | パッケージを受理できた |
| 7 | `review` | ③ | 変更内容の確認（差分） | 変更が 1 件以上あり、手動修正を開いていない |
| 8 | `output` | ④ | 出力ファイル名 | 名前が正しい（ファイル名のみ・元の拡張子） |
| 9 | `build` | ④ | （自動） | — |
| 10 | `done` | ④ | 出力フォルダを開く / 完了 | （［次へ］の位置は［完了］） |

**画面 0 は β1.10 の画面 1 と 2 の統合である。** 読み取り結果（モジュール名と行数、
`read.level` の伝え方）は同じ画面の折りたたみへ入れる。β1.10 §5.1.2 の 2 段階の
伝え分け（コードに疑いがある / 管理情報だけ）はそのまま維持する。

**消える画面**: β1.10 の画面 0（作業を選ぶ）と画面 2（読み取り結果の専用画面）。
**消える入口**: 「AIで相談する」「簡易モードで始める」。

### 2.3 分岐は 2 か所だけ

`nextIndex` が持つ分岐は次の 2 つに限る。

1. **画面 3 → 4**: 選んだひな形が `## 質問` を持つ場合、画面 4 の上部に質問欄が加わる
   （画面は増えない。β1.10 の質問専用画面は廃止し、希望動作入力と同じ面へ畳む）。
2. **画面 4 → 5 / 4 → 7**: 選んだひな形の `## エンジン` が `AI` なら 5 へ、
   `固定パス置換` なら 7 へ。**この分岐はユーザーに見えない。**

### 2.4 画面 4 の［次へ］条件（経路別）

条件は**すべての項を満たす**（`AND`）。「または」で緩めない。

| engine | 条件 | ボタン文言 |
|---|---|---|
| `AI` | (1) 選んだひな形の `## 質問` があるなら**全問に回答済み** **かつ** (2) 選んだ指摘の**全件**に希望動作が入力されている **かつ** (3) 選んだ指摘が 1 件以上 **または**「追加の要望」が非空 | ［次へ］ |
| `固定パス置換` | (1) `applied` のマッピング行が 1 行以上 **かつ** (2) `applied` の**全行**が §7.6 の検証に合格 | ［この内容で置き換える］ |

**`AI` の (2) と (3) の組み合わせに注意**: 「指摘を 3 件選んだが 1 件が空欄、
ただし追加の要望を 1 文字書いた」は**進めない**。空欄の選択を抱えたまま
依頼を出すと、AI はその指摘について何を求められているか分からない。
(3) は「何も選ばずに追加の要望だけで進む」を許すための項であって、
(2) を免除する項ではない。

固定パス置換のボタンを押すと、その場で置換を計算して画面 7 へ進む。
**別ウィンドウ・別モーダル・進捗ダイアログは出さない。**

### 2.5 戻る

［戻る］は実際に通った経路を逆にたどる（β1.10 と同じ history stack）。
画面 9（build）中だけは戻れない。

診断をやり直したいときは画面 2 へ戻って取り込み直す。ブックを読み込み直すと
診断以降の全状態を捨てる（取り込み済みがあれば確認ダイアログ）。

### 2.6 状態の帰属（β1.10 の不変条件を 2 段階へ拡張）

依頼 ID だけに紐づけると、**ID が同じまま前提が変わった**ときに古い結果が生き残る。
そこで各段階の成果物は、自分が答えた**前提一式のスナップショット**に帰属させる。

| 成果物 | 帰属する前提 |
|---|---|
| 診断パッケージ | ブックの内容署名 ＋ **環境定義の正準スナップショット** ＋ 診断依頼 ID |
| 改修パッケージ / 決定的置換の結果 | 診断結果の版 ＋ 選んだひな形の**ファイル名と内容** ＋ 全入力（質問の回答・選択した指摘・希望動作・追加の要望・マッピング） ＋ 改修依頼 ID |

- **環境定義の正準スナップショット**: `target-environment.json` の内容を
  §3.6 の整形へ通した結果の文字列。画面 1 へ入るたびファイルを読み直すため、
  読み直した結果がスナップショットと違えば「依頼を作り直す」条件になる（§4.2.1）。
  ファイルを編集して版が上がったのに古い依頼で診断を受け取る、という状態を作らない。
- **診断結果の版**: 診断を受理するたびに 1 つ増える整数。同じ診断依頼 ID へ
  取り込み直した場合でも版が変わるので、それに基づく改修入力と改修結果は無効になる。

無効化の規則（左が起きたら右を捨てる）:

| 起きたこと | 捨てるもの |
|---|---|
| ブックを読み込み直した | すべて（実行フォルダごと新しい実行） |
| 環境定義が変わった状態で画面 1 へ入った | 診断依頼から下流すべて |
| 「ほかに気になっていること」を変えて［依頼を作り直す］ | 同上 |
| 分割受理のチェックを切り替えた | 同上（受け取り済みの part も含む） |
| 診断を取り込み直した（版が上がった） | 選択・希望動作・追加の要望・改修依頼・改修パッケージ・決定的置換の結果・差分 |
| ひな形を選び直した（ファイル名または内容が変わった） | 質問の回答・選択・希望動作・追加の要望・マッピング・改修依頼から下流 |
| 画面 4 の入力を変えた（回答・選択・希望動作・追加の要望・マッピング） | 改修依頼・改修パッケージ・決定的置換の結果・差分・出力名 |
| `NEEDDECISION` を受理した | 改修パッケージ（差し戻しの質問は残す。§5.4.1） |

- 診断結果が無い状態で画面 3 以降へ入ることはできない。
- **ひな形は選んだ時点の内容をスナップショットする。** 画面 3 へ入るたび
  `presets/` を読み直すため、外部でファイルが変わっていれば内容が変わる。
  変わっていたら上表の「ひな形を選び直した」と同じ扱いにする。

#### 2.6.1 状態の確定はホストの成功後（transaction）

新しい依頼 ID・スナップショット・状態を、**ファイル書き出しが成功する前に確定しない**。

1. 画面 4 →5（または 1 への初回入場）で、入力のスナップショットを取る。
2. ホストへ書き出しを依頼する。この間、前進ボタンは `disabled`（二重押下を作らない）。
3. **ホストが成功を返してから**、新しい ID・スナップショット・下流の破棄を一度に確定する。
4. ホストが失敗を返したら、**ファイルも状態も 1 か所も変わっていない**。
   古い依頼 ID・古いファイル・古い結果がそのまま残る。

ホスト側の書き出しも同じ規律に従う。`diagnose-request.md` の世代交換・
`repair-request.md`・`diagnosis.md` は **一時ファイルへ書く → flush / close →
本来の名前へ置き換える**（β1.10 §5.4 の再ビルドの世代交換と同じ方式）。
途中で失敗しても前の世代が壊れない。

## 3. 想定動作環境（実データ）

### 3.1 ファイル

```
macrostudio/
└── environment/
    ├── target-environment.json   … 機械可読の正本（アプリが実行時に読む）
    └── SOURCES.md               … 出典・版管理・改訂履歴（人が読む・保守する）
```

**コード内に同じ内容を持たない。** C# にも JS にも fallback の既定値を置かない。
ファイルが無い・壊れている場合はアプリが止まる（§3.5）。

### 3.2 スキーマ（`schemaVersion: 1`）

```json
{
  "schemaVersion": 1,
  "profileId": "new-business-terminal",
  "displayName": "新しい業務端末",
  "revision": "2026-08-01",
  "summary": "EDR / DLP 管理下の Windows 端末。ブックは SharePoint / OneDrive 上に置かれる。",
  "sources": [
    { "id": "ms-preset-04", "origin": "macrostudio", "path": "presets/04_新しい端末で動くかを調べてもらう.md", "readAt": "2026-08-01" }
  ],
  "constraints": [
    {
      "key": "WIN32API_BLOCKED",
      "axis": "execution",
      "effect": "blocked",
      "title": "Win32 API の Declare 呼び出しが実行できない",
      "detail": "宣言だけでなく、その API を呼んでいる箇所も動かない。",
      "basis": "declared",
      "sourceIds": ["ms-preset-04", "devkit-analyze-edr"],
      "examples": ["Declare", "Declare PtrSafe"]
    }
  ]
}
```

| フィールド | 必須 | 規則 |
|---|---|---|
| `schemaVersion` | ○ | 整数。`1` 以外は**未知として拒否**（推測で読まない） |
| `profileId` | ○ | `/^[a-z][a-z0-9-]{2,63}$/` |
| `displayName` | ○ | 非空。画面に常時出る |
| `revision` | ○ | 非空。画面に常時出る |
| `summary` | ○ | 非空。1〜3 行 |
| `sources[]` | ○ | 1 件以上。`id` は非空かつ一意。`origin` / `path` / `readAt` 必須 |
| `constraints[]` | ○ | 1 件以上 |
| `constraints[].key` | ○ | `/^[A-Z][A-Z0-9_]{2,39}$/`。全体で一意。**診断契約の `ENVKEY` が参照する** |
| `constraints[].axis` | ○ | `execution` / `storage` / `host` / `components` / `office` / `platform` |
| `constraints[].effect` | ○ | `blocked`（動かない） / `changed`（動くが結果が変わる） / `uncertain`（確認が必要） |
| `constraints[].title` | ○ | 非空。1 行 |
| `constraints[].detail` | ○ | 非空 |
| `constraints[].basis` | ○ | `observed`（実測した） / `declared`（前提として宣言した） / `inferred`（設計上そうなるはず） |
| `constraints[].sourceIds` | ○ | 1 件以上。すべて `sources[].id` に存在すること |
| `constraints[].examples` | — | 文字列配列。**プロンプトへ渡す例示専用**。コードの走査には一切使わない |

### 3.3 同梱する内容の出典

初期値は次の 3 つの実物から抽出する（[AUDIT-BETA1.md](AUDIT-BETA1.md) §2）。

| sourceId | 出典 | 与えるもの |
|---|---|---|
| `ms-preset-04` | `macrostudio/presets/04_新しい端末で動くかを調べてもらう.md` | 5 つの前提（Win32 API / 外部プロセス / パスの URL 化 / 端末依存の固定値 / 古い部品） |
| `devkit-analyze-edr` `devkit-analyze-compat` `devkit-analyze-path` | `pub/vba-devkit/config/analyze.json` と `lib/Analyze.ps1` | 3 軸 38 項目の列挙と、`observed` / `inference` の別 |
| `datadesk-envtest` | `pub/datadesk/envtest/modules/*.ps1` | 環境事実集合の軸の語彙（runtime / office / webview / security / network / exe / communication）と `ok/missing/error` の記録規律 |

**`basis` の初期値はすべて `declared` または `inferred` である。**
`observed` を名乗る項目は初期状態では 0 件でよい。理由:
`datadesk/envtest/results/` は `.gitignore` されており実測結果が存在せず、
README が参照する `.repos/CONSTRAINTS.md` も存在しないため
（[AUDIT-BETA1.md](AUDIT-BETA1.md) §2.2.1）、**測っていないものを測ったと書かない**。

`vba-devkit` の `Basis = 'observed'` は「その検出パターンが検証で実際に立った」という
意味であって「対象端末でその制約が実測された」ではない。混同せずに `inferred` へ落とす。

### 3.4 読み込み

- 新 IPC action `getTargetEnvironment` → `{content}`（`environment/target-environment.json`
  を strict UTF-8 で毎回読み直す）。**ホストは中身を解釈しない**（§1.2 の継続）。
- 検証と解釈は `assets/js/target-environment.js` **だけ**が持つ。第 2 実装を作らない。
- 読み直す契機: 起動時と、画面 1（診断依頼）へ入るたび。ファイルを編集しても再起動不要。

### 3.5 fail-fast

次のいずれかで **E-ENV-01** とし、画面 1 にカードを出して**診断へ進めない**。
トーストで流さない。既定値へ落ちない。

- ファイルが無い / 読めない / strict UTF-8 として不正 / JSON として不正
- `schemaVersion` が `1` でない
- §3.2 の必須フィールド欠落・型不一致・列挙外の値
- `constraints[].key` の重複、または命名規則違反
- `sourceIds` に `sources[].id` へ存在しない id がある
- `constraints` が 0 件

カードには「何が起きたか」と「どのファイルを直せばよいか」を書く。
`environment\target-environment.json` の相対パスは出す（絶対パスは出さない）。

#### 3.5.1 失敗の内部 ID（利用者へは出さない）

**利用者が見るコードは `E-ENV-01` の 1 つだけ**である。これは変えない。
ただし検証の失敗には**内部 ID** を持たせ、`EnvironmentError` に
`validationId` として載せる。

| validationId | 条件 |
|---|---|
| `ENV-READ` | ファイルが無い / 読めない / strict UTF-8 として不正 |
| `ENV-JSON` | JSON として不正 |
| `ENV-SCHEMA` | `schemaVersion` が `1` でない |
| `ENV-FIELD` | 必須フィールドの欠落・型不一致 |
| `ENV-ENUM` | `axis` / `effect` / `basis` が列挙外 |
| `ENV-KEY` | `constraints[].key` の命名規則違反 |
| `ENV-KEYDUP` | `constraints[].key` の重複 |
| `ENV-SOURCE` | `sourceIds` が空、または `sources[].id` に存在しない |
| `ENV-SOURCEDUP` | `sources[].id` の重複 |
| `ENV-EMPTY` | `constraints` が 0 件 |

**なぜ要るか**: この節は 10 個の異なる条件を 1 つの利用者向けコードへ畳んでいる。
内部 ID が無いと、否定テストは「`E-ENV-01` で落ちた」としか言えず、
**意図した条件とは別の条件で落ちていても気づけない**
（例: 「key 重複」の fixture が、実は必須欄の書き損じで `ENV-FIELD` に落ちていても
テストは通る）。これは codex-implementer が C6 で指摘した
「負例が正しい理由で落ちたことを検査する」と同じ問題である。

各否定 fixture は**自分の `validationId` を名指しで assert する**
（[PLAN-BETA2.md](PLAN-BETA2.md) §4.1-2）。

### 3.6 プロンプトへの組み込み

診断テンプレート `templates/diagnose-template.txt` の変数 `{{TARGET_ENVIRONMENT}}` へ、
次の固定形式で差し込む（ASCII 罫線。全体をバイト単位で回帰テスト固定する）。

```
================================================================================
 TARGET ENVIRONMENT: 新しい業務端末 (new-business-terminal / rev 2026-08-01)
================================================================================
EDR / DLP 管理下の Windows 端末。ブックは SharePoint / OneDrive 上に置かれる。

[WIN32API_BLOCKED] execution / blocked / declared
  Win32 API の Declare 呼び出しが実行できない
  宣言だけでなく、その API を呼んでいる箇所も動かない。
  例: Declare, Declare PtrSafe

[SHELL_EXEC_BLOCKED] execution / blocked / declared
  外部プログラムの起動が実行できない
  Shell 関数、WScript.Shell、cmd /c による外部プロセスの起動が止められる。
  例: Shell, WScript.Shell, cmd /c
--------------------------------------------------------------------------------
 basis: observed=実測 / declared=前提として宣言 / inferred=設計上の推定
================================================================================
```

- 並び順は `axis` の定義順（`execution` → `storage` → `host` → `components` →
  `office` → `platform`）、同一 axis 内は `key` の昇順。**入力ファイルの並びに依存しない。**
- `examples` が無い項目は「例:」行を出さない。
- この整形は `target-environment.js` の `renderForPrompt()` だけが持つ。

## 4. 第 1 段階: AI 診断（事実監査）

### 4.1 この段階が決めること・決めないこと

| 決める | 決めない |
|---|---|
| マクロの目的 | 改修方針 |
| 処理の流れ | 改修後の動作予測 |
| 依存関係 | 「改修不要」の結論 |
| 対象環境で動くか（阻害要因の列挙） | どのモジュールをどう書き換えるか |

例外として「この監査範囲では動作阻害要因を確認できなかった」は結論として認める（§4.6）。

#### 4.4.1 META 行

1 行 1 指摘のメタ情報。**キーの順序・個数を固定**し、`key=value` を半角空白 1 つで区切る。
値に空白は入らない（入る値は TEXT ブロックへ置く）。欠落は `-` と書く。

| キー | 値 | 規則 |
|---|---|---|
| `CLASS` | `BLOCKER` / `DEFECT` / `CONDITIONAL` / `EXTERNAL` / `INFO` | 必須。列挙外は拒否 |
| `CONFIDENCE` | `CONFIRMED` / `LIKELY` / `UNVERIFIED` | 必須。列挙外は拒否 |
| `MODULE` | モジュール名 または `-` | `-` 以外は**添付したブックに実在する名前**（case-insensitive 照合）。実在しなければ拒否 |
| `PROC` | プロシージャ名 または `-` | VBA 識別子として妥当。**実在は照合しない**（プロシージャの列挙を持たないため。名乗りを事実として扱わず、画面では「AI が指した名前」として出す） |
| `LINES` | `12` / `12,13` / `12-20` / `-` | 正準 10 進・カンマ・ハイフンのみ。範囲は開始 ≤ 終了。**1 起点で、画面に出しているコード（先頭 Attribute ブロック除去後）の行番号**。`MODULE` の行数を超える値は拒否 |
| `ENVKEY` | 環境定義の `key` または `-` | `-` 以外は**読み込んだ環境定義に実在する key**。実在しなければ拒否 |

**該当箇所の整合規則**（要件 B「該当モジュール/プロシージャ/行を持たせる」を、
名乗るだけで通らないようにする）:

| 規則 | 検査 ID | 断る理由 |
|---|---|---|
| `PROC` が `-` でないなら `MODULE` も `-` でない | D23 | どのモジュールの話か分からないままプロシージャ名だけを名乗っている |
| `LINES` が `-` でないなら `MODULE` も `-` でない | D24 | どのモジュールの話か分からないまま行番号だけを名乗っている |
| `LINES` の全ての行番号が 1 以上かつ `MODULE` の可視行数以下 | D25 | 存在しない行を指している |

**なぜ 2 つに分けているか**（実装時に codex-implementer が指摘した点の記録）:
当初この規則は「`MODULE=-` なら `PROC` と `LINES` も `-`」と
「`PROC` か `LINES` が `-` でないなら `MODULE` も `-` でない」の 2 本だったが、
この 2 つは**対偶であり論理的に同値**である。したがって片方だけを破る入力は作れず、
「各検査に落ちる fixture を 1 件ずつ」の規律の下で一方の ID が到達不能になる。
**強制する不変条件は変えないまま**、offender となるフィールドで分割した。
`MODULE` だけを名乗り `PROC` / `LINES` が `-` の指摘は**正常**である
（モジュール単位までしか特定できていない、という事実の表明）。

**`CLASS` と `CONFIDENCE` の整合規則**: `CONFIDENCE=UNVERIFIED` の指摘は
`CLASS` が `CONDITIONAL` / `EXTERNAL` / `INFO` のいずれかでなければならない。
「確実に動かない」と「確認していない」を同時に名乗る指摘は受理しない
（要件「曖昧なものを断定しない」の機械的強制）。

**`CLASS=BLOCKER` の追加規則**: `ENVKEY` が `-` でなく、かつ**その環境制約の
`effect` が `blocked` であること**。`effect` が `changed` / `uncertain` の制約を
根拠に「対象環境では動かない」と表示するのは、環境定義が言っていないことを
言わせることになる。該当するなら `CLASS` は `CONDITIONAL` である。

#### 4.4.2 `CONFIDENCE` と `basis` は別のものである

混同しやすいので明示する。**この 2 つは別の主体の、別の対象への確からしさである。**

| | 誰の | 何に対する |
|---|---|---|
| `CONFIDENCE`（`META` の値） | **AI の** | **コードを読んだ結果**の確からしさ（この箇所が本当にそうなっているか） |
| `basis`（環境定義の値） | **私たちの** | **環境の前提**の確からしさ（対象端末で本当にそうなるか） |

したがって `CONFIDENCE=CONFIRMED` の指摘が `basis=inferred` の制約を指すことは
**矛盾ではない**。「コードにこの API 呼び出しが確かにある（CONFIRMED）。
その API が対象端末で止まるという前提は推定である（inferred）」という状態を表す。

画面はこの 2 つを**別のチップとして並べて出す**（§6.2）。片方だけを見せない。
`CLASS=BLOCKER` かつ `basis` が `observed` でない指摘には、
第二層に「この環境前提は実測ではありません」の 1 行を添える。

`DEFECT` に `CONFIDENCE=LIKELY` を許すのも同じ理由による。
`CLASS` は**問題の種類**（環境の阻害か、コード自体の不具合か）を表し、
`CONFIDENCE` は**その読み取りの確からしさ**を表す。
「データ損失を起こす不具合である可能性が高い」は意味のある状態であり、拒否しない。

#### 4.4.3 分類と優先順位

画面の表示順・重み付けはこの順に固定する（要件 B）。

| # | CLASS | 意味 | 画面 |
|---|---|---|---|
| 1 | `BLOCKER` | 環境上の阻害要因。対象環境では動かない | 常時展開 |
| 2 | `DEFECT` | 確定的なバグ／データ損失 | 常時展開 |
| 3 | `CONDITIONAL` | 条件付きリスク | 常時展開 |
| 4 | `EXTERNAL` | 外部前提・運用前提（人に聞かないと分からない） | 常時展開 |
| 5 | `INFO` | 補助情報（効率・可読性など） | **既定で折りたたみ** |

`INFO` は主結果ではない。件数だけ見出しに出し、開かなければ本文は見えない。

#### 4.5.1 数の読み方（`COMPLETE` と `PART` は別規則）

β1.10 は `COMPLETE` の数を `Number()` で変換して比較していたため、
`1.0` / `0x2` / `1e0` / `Infinity` を module 数と一致すれば受理していた
（[AUDIT-BETA1.md](AUDIT-BETA1.md) §1.4.1 A1）。
`/^\d+$/` を課すだけでは `01` が通るため、**それだけでは足りない**。

| 用途 | 規則 |
|---|---|
| `COMPLETE <n>` / `DIAG COMPLETE <n>` | **正準 10 進表記**: `/^(0\|[1-9][0-9]*)$/`。そのうえで `String(実際の件数) === <n>` の**文字列一致**で判定する。数値変換を一切経由しない。`01` / `1.0` / `0x2` / `1e0` / `+1` / 全角数字はすべて拒否 |
| `PART <番号> OF <合計>` | **β1.10 の既存挙動を変えない**。`/^\d+$/` の 0 起点整数として読み、`00` 表記を受理する。同じ part を `0` と `00` の両方で名乗ることは、正準化した値が一致するため**同一 index として扱う**（内容が同一なら冪等、異なれば conflict） |

区切り行そのものの読み方（前後の空白を無視し、語を空白で分割する）は β1.10 のまま変えない。
**したがって語の間の空白の数は検査対象にしない。** 検査するのは語の並びと各語の形である。

`FINDING <n>` / `DECISION <n>` の番号も正準 10 進表記とし、
`1` と `01` が同じパッケージに同居することを**拒否**する（D07 / §5.4.1）。
表示と並べ替えは正準化した数値で行い、パッケージ内の記載順には依存しない。

### 4.6 指摘が 0 件のとき

```
'@MACROSTUDIO <ID> DIAG BEGIN 1
（SECTION 4 種は必須。省略できない）
'@MACROSTUDIO <ID> DIAG NOFINDING SCOPE_CLEAR
'@MACROSTUDIO <ID> DIAG COMPLETE 0
'@MACROSTUDIO <ID> DIAG END
```

| `<理由>` | 意味 | 画面の伝え方 |
|---|---|---|
| `SCOPE_CLEAR` | この監査範囲では動作阻害要因を確認できなかった | 「この監査範囲では動作阻害要因を確認できませんでした。」 |
| `INSUFFICIENT` | 判断に必要な情報が足りない | 「判断に必要な情報が足りませんでした。」＋ ENVIRONMENT 節の本文を続けて出す |

- 4 つの SECTION は 0 件でも必須である。**指摘が無いことと、読んでいないことは違う。**
- `SCOPE_CLEAR` は「問題が無い」ではない。文言でも「確認できませんでした」と書き、
  「問題ありません」「改修不要です」とは書かない（§4.1）。
- 0 件でも画面 3 へ進める。ひな形（固定パス置換や自由記述）は選べる。
  一本道を 0 件で行き止まりにしない。

### 4.7 長い診断の分割受理

β1.10 §6.6 と**同じ機構・同じ語**を使う。`DIAG BEGIN` の直後に 1 行足すだけ。

```
'@MACROSTUDIO <ID> DIAG BEGIN 1
'@MACROSTUDIO <ID> PART 00 OF 03
```

**統合はテキストの連結ではない。** 各 part は自分の `DIAG BEGIN` / `DIAG END` /
`DIAG COMPLETE` を持つので、本文をそのまま繋ぐと統合後に `DIAG BEGIN` が
複数現れて D02 / D18 に違反する。**構造体として統合する。**

処理は 2 相に分ける。どの検査をどちらで行うかを次の表で固定する。

| 相 | 何をするか |
|---|---|
| **相 1 `parsePart`** | 1 つの返答を単独で解析し、その中で閉じている検査だけを行う |
| **相 2 `mergeParts`** | 全 part がそろった時点で構造体を統合し、全体でしか判定できない検査を行う |

| 検査 | 相 1（part ごと） | 相 2（統合後） |
|---|---|---|
| D01 依頼 ID | ○ | — |
| D02 `DIAG BEGIN`/`END` 対応 | ○（その part の中で） | — |
| D03 版 | ○ | 全 part で一致すること |
| D04 `SECTION` 4 種が揃う | **part 00 のみ**。01 以降は SECTION が 1 つでもあれば拒否 | ○（統合後に 4 種が揃っていること） |
| D05 `SECTION` 種別 | ○ | — |
| D06〜D17, D23〜D28 各 `FINDING` の内部 | ○ | — |
| D07 `FINDING` 番号の一意性 | ○（part 内） | ○（**全体**で一意。別 part の同番号は拒否） |
| D18/D19 `DIAG COMPLETE` | ○（**その part に含まれる件数**と一致） | — |
| D20/D21 `NOFINDING` | — | ○（**全体 0 件のときのみ**。§4.7.1） |
| D22 外側に sentinel が無い | ○ | — |
| `PART` の整合 | ○（1 本だけ・`/^\d+$/` の 10 進数字列・`0 ≤ 番号 < 合計`・`合計 ≥ 1`。**`00` 表記を受理する**。§4.5.1 の `PART` 規則） | ○（全 part で `<合計>` 一致・欠番なし） |

- `<番号>` は 0 起点、`<合計>` は 1 以上（読み方は §4.5.1 の `PART` 規則）。
- `DIAG COMPLETE <n>` は**その返答に含まれる指摘の件数**（β1.10 の `COMPLETE 1` と同じ考え方）。
  統合後の総件数を名乗る行は**存在しない**。総数の担保は `PART ... OF <合計>` が行う。
- 同じ番号の再送は、正規化後の本文が**完全に同一のときだけ**冪等に受け入れる。
  内容が違えば拒否し、集めた分は変えない。
- 欠番のまま先へ進めない。何番が足りないかを画面が名指しする。
- 全部そろったら番号順に統合する。**統合後の構造体は、同じ内容を一度で受け取った場合と
  完全に同一**でなければならない（要件 A「下流では同じ内部形式へ統合する」）。
  これをテストで固定する。
- **相 1 で通った検査を相 2 でもう一度回さない。** 二重拒否も取りこぼしも作らないよう、
  上の表が唯一の割り当てである。
- 分割を使うかどうかは画面 1 の折りたたみ内のチェック 1 つで選ぶ。ON にすると
  診断ひな形の `## 出力指示（分割）` が出力指示に入れ替わる。切り替えると
  それまでに受け取った part を捨てる（2 つの返し方を混ぜない。§4.2.1）。

#### 4.7.1 分割時の 0 件

`NOFINDING` は**全体で 0 件のときにだけ**成立する。したがって分割形式では
`PART 0 OF 1`（＝ part が 1 つしかない）のときにのみ許す。

- `PART 0 OF 3` で `DIAG COMPLETE 0` かつ `NOFINDING` は**拒否**する
  （残り 2 つに指摘があるかもしれない状態で「指摘なし」を名乗っている）。
- 途中の part が `DIAG COMPLETE 0` で `NOFINDING` を持たないことは**正常**である
  （その返答には指摘が入っていなかっただけ）。
- 全 part がそろって総件数が 0 なのに、どの part も `NOFINDING` を持たない場合は
  D20 で拒否する（無言の 0 件）。

### 4.8 受理後の成果物

診断を受理した時点で、実行フォルダへ `diagnosis.md` を書き出す。
人が読める整形（見出し＋箇条書き）で、META の値と 4 つの TEXT をそのまま載せる。
これは記録であり、以降の処理はこのファイルを読まない（正本はメモリ上の内部形式）。

## 6. UI 仕様

### 6.1 原則

1. **一つの中央作業面。** 最大幅 880px の 1 カラム。左右にペインを持たない
   （β1.10 の確認画面のモジュール一覧＋diff の 2 ペインだけは例外として維持する）。
2. **必須データは最初から表示する。** 対象ブック名、想定環境の名前と版、
   進捗 4 手順、この画面ですること、対処が必要な警告。
3. **任意データは入口が明確で、既定は畳む。** ラベルは中身を名乗る
   （「詳細設定」「オプション」は禁止）。**その場で開く。**
   別設定画面・別モーダル・別トップ動線へ追い出さない。
4. **主結果が先、証拠は淡い第二層。** 第二層は `--text-sub` / 12〜13px /
   左 3px のレール付きブロックで、地の色は変えない。
5. **入れ子は 1 段まで。** 開閉領域の中に開閉領域を置かない。
   例外は指摘一覧の 1 か所だけとし、`INFO` グループ（1 段目）の中の各指摘（2 段目）に限る。
6. 警告と、操作がまだできない理由は、開閉領域へ入れない。

### 6.2 分類と確度の視覚語彙

β1.10 の状態辞書（青=作業中 / 緑=完了 / 灰=未処理 / 赤=削除・失敗）を壊さない。
診断の分類には**別の軸**を割り当て、既存の色に意味を足さない。

| CLASS | チップ | 色トークン |
|---|---|---|
| `BLOCKER` | `阻害` | `--danger` 塗り・白字 |
| `DEFECT` | `不具合` | `--danger-text` 文字・`--danger-soft` 地 |
| `CONDITIONAL` | `条件付き` | `--accent-text` 文字・`--accent-soft` 地 |
| `EXTERNAL` | `前提` | `--text-sub` 文字・`--surface-hover` 地 |
| `INFO` | `補助` | `--text-muted` 文字・輪郭のみ |

| CONFIDENCE | チップ |
|---|---|
| `CONFIRMED` | `確認済み` |
| `LIKELY` | `可能性高` |
| `UNVERIFIED` | `未確認` |

確度チップは常に分類チップの右、`--type-micro`、輪郭のみ。塗らない。

### 6.3 アクセシビリティ（実測で確認する項目）

| 項目 | 要求 |
|---|---|
| 開閉 | `<button aria-expanded aria-controls="…">` ＋ 制御対象 `id`。畳んだ中身は **`hidden` 属性（＝`display:none`）** でタブ順と読み上げから外す。**β1.10 §4.1 の `visibility: hidden` は使わない** — 場所を占有し続けるため高さが消えず、§6.4 の高さ計算が成立しない |
| キーボード | 添付 → 診断依頼 → 取り込み → 指摘選択 → 希望動作入力 → 依頼 → 取り込み → 差分 → 出力名 → ビルドまで**マウス無し**で到達できる |
| 指摘一覧 | 上下矢印で行間移動、Enter / Space で開閉、Tab は一覧全体を 1 ストップとして扱わず各行のボタンを順に辿る |
| フォーカス | 画面遷移後は `main` へフォーカスを移す。開閉を閉じたときはトリガーへ戻す。フォーカスリングは `--focus-ring` |
| IME | 変換中（`compositionstart` 〜 `compositionend`）に Enter で［次へ］が発火しない。変換確定の Enter を送信に使わない。希望動作欄・追加の要望欄・出力名欄すべてで確認する |

### 6.4 狭い画面・長い内容

**縦スクロールの器はちょうど 1 つである。**

- トップバー・進捗バー・画面見出し・フッターの操作領域は**固定**。
- その間の**画面本文（`.screen-body`）が唯一の縦スクロール器**（`overflow-y: auto`）。
  `body` は決してスクロールしない。
- 「指摘一覧だけがスクロールする」方式は**採らない**。画面 4 が最長になる状態
  （質問全件 ＋ 選択した指摘ごとの希望動作欄 ＋ 追加の要望 ＋ 維持すること、
  あるいはマッピング行が数十行）では、一覧だけを縮めても他が収まらない。
- 画面 3 は、画面本文の中で**指摘一覧に残りの高さを配る**
  （結論帯と概要 4 行と ひな形カードを引いた残り）。一覧が短ければ器も短くなる。
- **フォーカス移動時のスクロール**: キーボードで画面本文の外にある要素へ移ったとき、
  ブラウザ既定の `scrollIntoView` に任せず、`.screen-body` の中だけをスクロールさせる。
  固定領域がずれないことをテストで確認する。
- 幅 1100px 未満で、指摘行の第二層が 2 列（該当箇所 / 根拠）から 1 列へ落ちる。
- 幅 1024px 未満で、結論帯の件数チップが 2 行へ折り返す。
- 長い行（パス・診断本文・コード）は**それぞれの領域内で横スクロール**する。
  `body` は横スクロールしない。
- 指摘が 0 件のときも一覧の枠は出し、「この監査範囲では動作阻害要因を確認できませんでした。」
  を中に置く（空の枠を消して画面を作り替えない）。

### 7.3 字句解析（`assets/js/vba-lexer.js`）

**正規表現で行を眺める方式は採らない。** `pub/vba-devkit` の
`(?mi)^[^''\r\n]*"[A-Z]:\\"` 方式は、文字列中のアポストロフィ（`"Don't"`）で誤爆し、
`REM` コメントを避けられず、行継続で分断されたパス連結を追えない
（[AUDIT-BETA1.md](AUDIT-BETA1.md) §2.1）。**書き換えるツールにこの精度は足りない。**

物理行ごとに 1 文字ずつ走査し、次の 3 種のトークンへ分ける。

| kind | 規則 |
|---|---|
| `string` | `code` 状態の `"` で開始。`""` は文字列中のダブルクォート 1 個。単独の `"` で終了。**物理行をまたがない** |
| `comment` | `code` 状態の `'` から行末まで。加えて、**文の先頭**の `REM` に続く空白または行末から行末まで（大小無視） |
| `bracket` | `code` 状態の `[` から対応する `]` まで（VBA の外部識別子・`Evaluate` 短縮形）。**この中では `'` も `"` も特別扱いしない** |
| `code` | それ以外 |

補足規則（いずれも実装とテストの対象）:

- **「文の先頭」の定義**: 次のいずれかの直後（空白は読み飛ばす）。
  1. 物理行の先頭
  2. `code` 状態の `:`（文区切り）の直後。ラベル行 `Label1:` の後もこれに当たる
  3. **物理行の先頭の空白に続く数字行ラベルの直後**（`100 Rem "C:\secret"`）。
     VBA は行番号ラベルを許すため、これを文の先頭として扱わないと
     `100 Rem` の後ろの文字列を候補にしてしまう。
     判定は `/^[ \t]*\d+[ \t]+/` に一致する部分の直後（`100 GoTo 200` も同じ形）。
     式の中の数字（`x = 100 + 1`）は行頭ではないのでこれに当たらない。

  `REMark` のような識別子はコメントにならない
  （`REM` の直後が空白か行末のときだけコメント）。
- **日付リテラル `#2026-08-01#`**: `code` として扱ってよい。中に `"` も `'` も現れないため、
  文字列・コメントの判定を乱さない。特別な状態を持たない。
- **条件付きコンパイル `#If` / `#ElseIf` / `#Else` / `#End If` / `#Const`**:
  字句としては通常の `code`。ただし入れ子の深さを数え、
  `#If ... Then` 〜 `#End If` の**内側にある出現**には印を付け、
  §7.5 の根拠表示に「条件付きコンパイルの内側」と出す（コンパイルされない可能性を
  利用者へ伝えるため。置換の可否は変えない）。
  - `#ElseIf` / `#Else` は深さを変えない。`#If` で +1、`#End If` で −1。
  - **釣り合っていない場合**（`#End If` が多い、または `#If` が閉じないままモジュールが終わる）は、
    そのモジュールの**全出現を `ambiguous` にして鍵を掛ける**（安全側）。
    深さを推測して続行しない。
- 文字列が閉じないまま行末に達した場合、その行を `unterminatedString` として印を付け、
  その行の候補はすべて `ambiguous` にする（VBA としても構文エラーであり、触らない）。
  同様に `]` が閉じないまま行末に達した行も `unterminatedBracket` として同じ扱いにする。
- **論理行**: `code` 状態で、行末が空白 + `_` で終わる物理行は次の物理行へ続く。
  文字列中・コメント中・`bracket` 中の `_` は継続ではない。
  論理行は「根拠の表示」と「連結されたパスの検出」に使う。
  置換は常に**物理行の中のトークン位置**に対して行う。
- **可逆性**: トークン列を順に連結すると元の物理行が
  **UTF-16 文字列として完全一致で**復元できること（§7.3.1）。
  これをテストで固定する（`test-vba-lexer.js`）。字句解析が壊れていれば、
  置換より先にこの検査が落ちる。

### 7.3.1 座標系（曖昧さを残さないための定義）

| 概念 | 定義 |
|---|---|
| 対象テキスト | モジュールの**可視コード**（先頭 Attribute ブロック除去後）。β1.10 §8 と同じく改行は CRLF に正規化済み |
| `line` | **1 起点**の物理行番号 |
| `column` | **0 起点**の、その物理行内の **UTF-16 コードユニット**オフセット |
| 行の分割・再結合 | CRLF で分割し、CRLF で結合する。末尾の CRLF の有無は入力のまま保つ |
| 「元と同じ」の意味 | **UTF-16 文字列としての完全一致**。「1 バイトも違わない」という言い方は、
デコード後の JS 文字列に対しては不正確なので使わない |

サロゲートペア（絵文字・一部の漢字）を含む行でも `column` はコードユニット数で数える。
`test-vba-lexer.js` の可逆性検査に、CRLF / LF のみ / 末尾改行なし / 日本語 /
サロゲートペアを前置した行の fixture を必ず入れる。

### 7.4 候補の検出

**`string` トークンだけを見る。`comment` / `code` / `bracket` は候補にしない。**
変数名・プロシージャ名・コメント・外部識別子は決して置換対象にならない。

まず「そもそも候補か」を決める。**次の述語が偽なら、その文字列は候補にならない**
（`ambiguous` にもならない。一覧に出さない）。

```
isPathish(value) =
     value に "\" が含まれる
  || value に "/" が含まれる
  || /%[A-Za-z_][A-Za-z0-9_()]*%/ に一致する部分がある
  || /\.[A-Za-z0-9]{1,8}$/ に一致する（末尾がファイル拡張子の形）
```

候補になった文字列に、**出現ごとに**次の順で class を与える。
最初に当たったものを採る。正規表現はコードブロックで示す（表内で `|` を書くと
markdown の列区切りと衝突するため）。

```
P-DRIVE-01  driveAbsolute  /^[A-Za-z]:[\\/]/
P-UNC-01    unc            /^\\\\[^\\]/
P-URL-01    url            /^(?:https?|ftp):\/\//i
P-ENV-01    envVar         /%[A-Za-z_][A-Za-z0-9_()]*%/
P-KNOWN-01  knownFolder    大小無視で "\Users\" "\Desktop" "\Documents"
                           "\AppData" "\Program Files" のいずれかを含む
P-FRAG-01   fragment       "\" か "/" を含み、同じ論理行で "&" により連結されている
P-BARE-01   bareName       区切り文字を含まず、同じ論理行に
                           Workbooks.Open / Dir / SaveAs / Open(For) /
                           FileSystemObject / GetObject のいずれかがある
P-AMB-01    ambiguous      isPathish だが上のどれにも当たらない
P-AMB-02    ambiguous      unterminatedString / unterminatedBracket の行にある
                           （この規則は他のすべてに優先する）
```

| class | 既定の扱い |
|---|---|
| `driveAbsolute` `unc` `url` `envVar` | 入力欄が開いた状態で提示 |
| `knownFolder` `fragment` `bareName` `ambiguous` | **要確認**（既定は鍵付き。§7.6） |

**`envVar` の範囲を絞った理由**: 「同じ論理行に `Environ` がある」を条件にすると、
`Environ("APPDATA")` の `"APPDATA"`（環境変数の**名前**であってパスではない）まで
候補になる。判定は**その文字列自身が `%NAME%` を含むか**だけにする。

### 7.5 集約と根拠の表示

- **集約の鍵は「値そのもの」だけである**（`groupKey = 値`）。class は鍵に入れない。
  同じ値が文脈によって別の class に分類されうるため、`class:値` を鍵にすると
  「同一値ごとに 1 行」が破れる。
- **グループの class は、そのグループの出現が持つ class のうち最も優先度の高いもの**
  （§7.4 の並び順）。各出現は自分の class と規則 ID を保持し続ける。
- **大文字小文字を区別しない集約は行わない**（トグルを置かない）。
  `C:\Data` と `c:\data` は別の行として出す。
  理由: まとめてしまうと 1 行が持つ「元の値」が 1 つに決まらず、
  §7.7 の「記録した値と完全一致」という適用条件を両方の綴りに対して満たせなくなる。
  綴りが 2 つあることは事実であり、事実のまま 2 行で見せる。
- 各行に出す（常時表示）: 値 ・ グループの class の日本語名 ・ 出現件数。
- 行を開くと第二層（出現箇所ごと）: モジュール名 ・ プロシージャ名 ・ 物理行番号 ・
  その論理行の全文（候補トークンを強調）・ 規則 ID ・
  条件付きコンパイルの内側なら「条件付きコンパイルの内側」の注記。

#### 7.5.2 `vba-highlight.js` と `vba-lexer.js` の責務境界

β2 は VBA を字句に分ける実装を**2 つ持つことになる**。既存の
`assets/js/vba-highlight.js`（93〜117 行目に独自の comment / string 判定を持つ）と、
新設の `assets/js/vba-lexer.js` である。**これは意図した二重化であり、
責務を分けることで成立させる。**

| 実装 | 用途 | 誤ったときに起きること |
|---|---|---|
| `vba-highlight.js` | **表示の着色**（diff ビュー・差分レポート HTML） | 色が少し違う。コードは変わらない |
| `vba-lexer.js` | **置換の対象決定**（候補検出・適用） | コメントや識別子を書き換える |

規律:

- **マッピング画面の根拠表示で候補トークンを強調するのは `vba-lexer.js` のスパンである。**
  `vba-highlight.js` の判定を使ってはならない。使うと「コメントとして着色されている
  文字列が置換対象として並ぶ」という、利用者から見て矛盾した画面になる。
  着色そのもの（キーワードの色など）は `vba-highlight.js` に任せてよいが、
  **候補の強調範囲は必ず `vba-lexer.js` から来る**。
- 2 つを一致させる検査は**置かない**。`vba-highlight.js` は β1.10 の表示用ヒューリスティックで、
  `100 Rem "..."` や `[Don't]` を `vba-lexer.js` ほど正しく扱わない。
  一致を要求すれば、正しい側を退化させるか、`vba-highlight.js` を作り直すことになる。
  **後者は差分レポートのバイト固定回帰（`test-diff-report-toggle.js`）に波及するため
  β2.00 のスコープ外**とする。
- したがって `vba-highlight.js` は**触らない**。責務が違うので触る理由が無い。
- 将来 `vba-highlight.js` を `vba-lexer.js` の上の描画層へ統合するのは妥当な整理だが、
  それは差分レポートの再固定を伴う別の作業である。

#### 7.5.1 プロシージャ名の決め方

字句解析の `code` トークンから宣言行を拾う。**開始だけでなく終了も追う。**

- 開始: 省略可能な `Public` / `Private` / `Friend` / `Static` に続く
  `Sub` / `Function` / `Property Get` / `Property Let` / `Property Set`。
- 終了: 対応する `End Sub` / `End Function` / `End Property`。
- 終了行より後、次の開始行より前（＝モジュールレベル）にある出現の
  プロシージャ名は `-` とする。**直近の宣言を無条件に当てない**
  （`End Sub` の後の宣言セクションが前のプロシージャに誤帰属するため）。
- 見つからなければ `-`（推測しない）。

### 7.6 マッピングの入力と検証

各行は `applied`（この行を置き換えるか）を持つ。**初期値はすべての class で `false`。**
class によって違うのは入力欄が最初から開いているか、鍵が掛かっているかだけである。

- `driveAbsolute` / `unc` / `url` / `envVar`: 入力欄は開いている。値を入れると
  `applied` が `true` になる。空にすれば `false` に戻る。
- `knownFolder` / `fragment` / `bareName` / `ambiguous`: 行内のチェック
  「この候補も置き換える」を入れて初めて入力欄が開く。チェックを入れると
  その行の第二層（根拠）が自動的に開く。

**検証は `applied` が `true` の行だけに対して行う。** `false` の行は検証対象外であり、
置換もされない。

| # | 検証（`applied` の行のみ） | 失敗時 |
|---|---|---|
| M01 | 新しい値が非空 | 行に印を付け、［置き換える］を無効 |
| M02 | 制御文字を含まない（U+0000〜U+001F と U+007F。CR / LF / TAB を含む） | 同上 |
| M03 | 長さ 1024 文字（UTF-16 コードユニット）以下 | 同上 |
| M04 | 元の class が `driveAbsolute` / `unc` / `url` のとき、新しい値が**絶対位置 3 分類**（`P-DRIVE-01` / `P-UNC-01` / `P-URL-01` のいずれか）に分類される | **要確認**の印を付け、行内チェック「入力した値が場所の形になっていないことを確認した」を入れるまで無効 |

- M04 の判定に使うのは**この 3 規則専用の分類器**であり、§7.4 の 8 分類ではない。
  新しい値が `fragment` や `bareName` に見えるかは問わない。
- **3 分類の内側での種類の変化は M04 の失敗ではない。**
  `driveAbsolute` → `url`（例: `C:\data\` → `https://…/data/`）は
  **このひな形が存在する第一の目的**（環境制約 `BOOK_PATH_IS_URL`）であり、
  確認チェックを要求しない。要求すると、機能の主目的を果たすたびに
  行の数だけ余分な操作が要ることになる。
- 種類が変わったことは**非ブロッキングの情報**として行内に 1 行出す
  （例: 「ドライブのパスから URL に変わります」）。**ゲートにしない。**
  URL 化に伴う `Dir()` / `ChDir` / `CurDir` の破綻は
  第 1 段階の診断が `DIR_EXISTENCE_CHECK` / `CURDIR_CHDIR` として既に伝えている。
  同じ判断をマッピング画面でもう一度ゲートとして課すのは、
  **ツールが良し悪しを決めること**であり §1.1 に反する。
- M04 が本当に止めたいのは「場所の形をしていない値を入れた」場合
  （例: `C:\data\` → `hello`）である。
- **`applied` の行が 1 行以上あること**が画面 4 の［置き換える］の有効条件である（§2.4）。
- 入力された値は VBA 文字列リテラルとして書き戻すとき `"` を `""` へ機械的に退避する。
  それ以外の加工（末尾 `\` の付与・正規化・大小変換）は**一切しない**。
- **自由文字列の一括置換 UI は作らない。** 置換の単位は常に「検出したトークンの集約行」であり、
  ユーザーが任意の検索文字列を入力する欄は存在しない。
- ［すべて置き換える］のような一括ボタンを置かない。

**不変条件（検証 ID ではない）**: 2 行以上が同じ新しい値を指してよい。
統合は正常な使い方であり、拒否条件を持たない。
そのため**これに失敗する fixture は存在せず、M 番号を与えない**。

### 7.7 適用（`assets/js/path-map.js`）

**必ず「全部を検査してから、全部を作って、最後に一度だけ確定する」の 3 相で行う。**
途中で状態へ書き戻さない。

**相 1 — preflight（何も変えない）**

1. 対象モジュールを**添付時のコード**から字句解析し直す（§7.7.1）。
2. `applied` の行が持つ全出現について、`(モジュール, line, column)` のトークンを取り出し、
   その値が記録した値と**完全一致**することを確認する。
3. 1 か所でも一致しなければ **E-MAP-02** で中止する。
   **このときアプリの状態は 1 か所も変わっていない**（テストで deep-equal を検査する）。

**相 2 — 再構築（コピーの上でだけ行う）**

4. 一致したトークンの**スパンだけ**を新しいリテラルへ差し替え、
   物理行をトークン列から組み立て直し、CRLF で結合して**新しいモジュール本文を作る**。
   元のモジュールオブジェクトは変更しない。
   - **列オフセットを使った逐次置換をしない。** 置換で長さが変わると後続の列がずれるため、
     常に「トークン列を作り直して 1 回で連結する」方式にする。
     この方式なら 1 行に何個あってもずれは原理的に発生しない。
5. 全モジュールの再構築が成功するまで、何も確定しない。

**相 3 — 確定（1 回だけ）**

6. 出来上がったモジュール集合を**一括で**状態へ入れる。
7. 画面と同じ `diff.js` で差分を計算し、画面 7 へ進む。
   以降はビルド・検証・出力・差分レポートまで AI 経路と同一である。
8. `result.md` にマッピング表を書く（class / 旧値 / 新値 / 件数 / 出現箇所の一覧）。
9. ログには**件数・class・モジュール名だけ**を書く。値は書かない
   （パスは利用者名・サーバ名を含みうる。β1.10 §7.6 の「コード本文は記録しない」の継続）。

#### 7.7.1 やり直し（画面 7 から戻ってきたとき）

候補の検出と適用は**常に添付時のコード（`attachBook` が返した `module.code`）から
計算する**。前回の置換結果や手動修正を入力にしない。
そうしないと、旧い値がすでに消えているために E-MAP-02 が必ず起き、
あるいは手動修正を黙って捨てることになる。

- 画面 4 へ戻った時点で、マッピングの入力内容（`applied` と新しい値）は保持する。
- ［置き換える］を押し直すと、添付時のコードから作り直した結果で
  **前回の置換結果を丸ごと置き換える**。
- そのとき手動修正（画面 7 の編集）が残っていれば、
  **実行前に確認ダイアログを出す**（β1.10 の `edit-discard-modal` と同じ型）。
  ［破棄して置き換える］を押したときだけ進む。黙って捨てない。

### 7.8 内部契約（将来の汎用マッピングのために固定する）

```json
{
  "schemaVersion": 1,
  "templateKey": "fixed-path-replace",
  "rows": [
    {
      "groupKey": "C:\\data\\",
      "class": "driveAbsolute",
      "from": "C:\\data\\",
      "to": "https://contoso.sharepoint.com/sites/eigyo/Shared Documents/data/",
      "applied": true,
      "occurrences": [
        { "module": "MonthlyReport", "procedure": "LoadSource", "line": 42, "column": 21,
          "class": "driveAbsolute", "ruleId": "P-DRIVE-01", "inConditional": false }
      ]
    }
  ]
}
```

- `groupKey` は**値そのものだけ**（§7.5）。`class:値` にしない。
- `rows[].class` は**そのグループの出現が持つ class のうち最も優先度の高いもの**。
- `occurrences[].class` と `ruleId` は**出現ごとの**分類であり、`rows[].class` と
  異なることがある（同じ値が文脈によって別の class に当たるため）。
- `occurrences[].line` は 1 起点、`column` は 0 起点 UTF-16 コードユニット（§7.3.1）。
- `inConditional` は `#If`〜`#End If` の内側かどうか（§7.3 / §7.5 の根拠表示に使う）。

この形は engine に依存しない。将来ほかの決定的置換（接続文字列・プリンタ名など）を
足すときも、同じ `rows` 構造と同じ画面部品を使い、`templateKey` と検出規則だけを替える。
**その拡張は β2.00 のスコープ外である。**

### 8.5 クリップボードの競合耐性

**背景（実測）**: codex-implementer が β1.10 の実 WebView2 試験を走らせたところ、
`test-flow-webview.ps1` が 3 回連続で失敗した。原因は製品のアサーション到達前に
WPF の `Clipboard.SetText` / `GetText` が `0x800401D0`（`CLIPBRD_E_CANT_OPEN`）を
返したことで、試験後の `GetOpenClipboardWindow` は 0 だった。
つまり**恒常的な占有ではなく、他プロセスとの一時的な競合**である。

β2.00 は AI との受け渡しをクリップボードと添付ファイルで行い続ける（§11）。
受け渡しは一本道の途中に**2 回**ある（診断依頼・改修依頼）ため、
β1.10 より競合に当たる機会が増える。したがって次を製品側に入れる。

1. **有界の再試行**: `04_HostServices.cs` の `Clipboard.SetText` / `GetText` を
   **最大 10 回呼び出す**（＝待ちは最大 9 回・各 50ms・合計 450ms）。STA スレッド上のまま。
   利用者から見て「固まった」と感じる長さにしない。
   - **再試行するのは `HRESULT 0x800401D0`（`CLIPBRD_E_CANT_OPEN`）だけ。**
     それ以外の例外は 1 回目で即座に失敗させる。
     区別しない再試行は、本当の失敗を 450ms 遅らせるだけで何も救わない。
   - 実装は再試行の中身を差し替えられる内部ヘルパー
     （操作を delegate で受ける形）にする。テストが呼び出し回数と HRESULT を
     決定的に検査できるようにするためで、実クリップボードの占有再現に依存させない。
   - **各回で占有者を記録する**: 再試行のたびに `GetOpenClipboardWindow()` を取り、
     0 でなければ `GetWindowThreadProcessId` からプロセス名と PID を得る。
     最終失敗時に WARN でログへ残す。
     **450ms を超える競合は実測で確認済み**（[DECISIONS-BETA2.md](DECISIONS-BETA2.md) D-14）
     なので、「誰が掴んでいたか」は利用者にとっても運用にとっても必要な事実である。
     ログにはプロセス名と PID だけを書く（ウィンドウタイトルは書かない。
     他アプリの文書名が漏れうるため）。
2. **最後まで失敗したら事実として出す**: 書き込み失敗は既存の `E-GEN-03`、
   読み取り失敗は新設の `E-GEN-04`。**黙って成功にしない・黙って空文字を返さない。**
   β1.10 の `readClipboard` は空を `{text:""}` として返すが、
   これは「空だった」ときの正常応答であり、**例外を空へ潰してはならない**。
3. **復旧の導線を画面に出す**: コピー失敗のトーストに「もう一度コピー」を、
   取り込み失敗のトーストに「`Ctrl+V` でも貼り付けられます」を添える。
   `Ctrl+V` の `paste` イベント経路は OS のクリップボード API を通らないため、
   ボタン経路が競合で落ちても貼り付けは成立する（β1.10 §7.3 の二経路がここで効く）。
4. **試験側**: 実 WebView2 試験のクリップボード操作にも同じ有界再試行を入れる。
   **再試行を尽くしても失敗したら試験は失敗させる**（緑にするための緩和ではない）。
   再試行が発生した回数を試験ログへ出し、フレークを見えなくしない。
