# MacroDesk 仕様書（v1）

Excel マクロ改修支援ツール MacroDesk の仕様書。
開発者向けの制約と手順は [DEVELOPMENT.md](DEVELOPMENT.md)、利用者向けの説明は
[../README.md](../README.md) を参照。

---

## 1. 目的と中核思想

### 1.1 目的

Excel マクロ（VBA）の改修を支援する GUI ツール。使用者は VBE を一度も開かずに
マクロを改修できる。

改修内容そのものは限定しない。改修マニュアル（プリセット）を差し替えれば、
固定パスの差し替え、コマンド実行（Shell / WScript / mshta 等）の見直し、
命名規則の統一など、任意の目的に使える。同梱の
`presets\サンプル_新端末移行.md` はその一例である。

改修の判断には Microsoft 365 Copilot Chat を外部脳として使う。ツールが動作する
端末にローカル AI が無くても成立させるための構成である。

### 1.2 中核思想

**ツールは判断を持たない。** 判断はすべて Copilot に外部化し、ツールは判断材料を
運ぶ配管に徹する。

- 「プリセット」は検出ルールやコード置換規則では**ない**。改修マニュアル本文を、
  Copilot に渡す参考資料としてプロンプト入力欄に流し込むだけ。
- 「依頼テンプレート」は `templates\request-template.txt` に置く生成ファイル全体の
  ひな型であり、プリセットとは役割が異なる。AI の種類や渡し方に合わせて使用者が編集できる。
- どこが改修対象か・どう直すかの判断は Copilot がやる。ツールは該当箇所を検出しない。
- Copilot の返答をツールは解釈しない（パースしない）。人間が読んで、GUI で
  モジュールを選んで貼る。**選ぶ行為そのものが確認**になっている。
  間違えたら diff が真っ赤になって気づける。
- 結果としてツールは汎用化される。別のマニュアルを差せば別目的に使える。
  ツール側のコードは変わらない。

この思想から導かれる実装上の線引き（本書での用語）:

- **禁止（判断）**: 返答テキストからモジュール名・コードブロックを抽出する、
  変更内容を要約する、対象モジュールを推定する、といった「意味の解釈」。
- **許可（帳簿付け）**: 貼り付けテキストの改行正規化、コードフェンス行の除去、
  `Attribute VB_` 行の機械的な除去・再付与、貼った結果の diff 計算。
  これらは入力の意味を解釈せず、決まった規則を機械的に適用するだけの処理。
  （個別の規則は §8 に列挙。ここに無い正規化を実装時に増やさないこと）

### 1.3 UI 設計原則

**押していいものが常に画面に 1 個だけ光っている**状態を目指す。
迷いどころを構造的に消す。各画面のグロー対象は §5 に明記する。

## 2. 全体構成

### 2.1 技術構成

**PowerShell 5.1 + Add-Type(C#) + WPF + WebView2** のハイブリッド構成。

- `launch.vbs` で黒画面を一切出さずに起動。配布物の起動方法は launch.vbs
  ダブルクリックの一択（開発時のみ launch.bat でコンソール表示）。
- UI の実体は WebView2 内の HTML/CSS/JS。XAML（WPF）は殻。
- dotnet SDK 不要。フォルダをコピーするだけで動くこと。
- WebView2 DLL（SDK 1.0.3856.49）をリポジトリに同梱する。

### 2.2 外部依存を持たない

MacroDesk は単体で完結し、実行時に外部ライブラリを必要としない。

- VBA の抽出・書き戻し（OLE2 複合ドキュメントの読み書き、MS-OVBA 圧縮ストリームの
  展開・再圧縮）は **MacroDesk 自身の実装**として `src/` に持つ。
- diff アルゴリズムと VBA シンタックスハイライトも自前実装（`assets/js/`）。
- 実行時依存はリポジトリ同梱の WebView2 DLL と OS 標準コンポーネントのみ。

### 2.3 エンジンの実装位置

エンジン（OLE2 / VBA 圧縮 / 書き戻し）は、ホストと同じ Add-Type でコンパイルする
**C# クラスとして src/ 内に実装**する（子プロセスや別モジュールを作らない）。

理由:
- 中核はバイト列処理であり、C# で書くのが最も素直。
- 子 PowerShell プロセス + JSON ファイル受け渡しの複雑さ（起動待ち・文字コード・
  一時ファイル管理）が丸ごと消える。
- GUI から切り離した検証は、同じ src/*.cs を Add-Type するヘッドレスの
  テストスクリプト（tests/）で行える。

### 2.4 リポジトリ構成

```
macrodesk/
├── launch.vbs               # 本番起動（黒画面なし）
├── launch.bat               # 開発起動（コンソールあり）
├── macrodesk.ps1            # ホスト: src/*.cs を集約 → Add-Type → App.Run
├── src/                     # C#（ホスト + エンジン）。ASCII のみ、C# 5.0 構文
│   ├── 01_App.cs            # エントリ。AssemblyResolve、STA スレッド、WebView2 ランタイム確認
│   ├── 02_MainWindow.cs     # WPF 窓 + WebView2 + 仮想ホスト + D&D 受け
│   ├── 03_MessageRouter.cs  # JS⇔C# の id 付き request/response IPC
│   ├── 04_HostServices.cs   # ダイアログ、クリップボード、explorer /select、依頼・差分ファイル出力、template / presets 読み、ログ
│   ├── 05_Ole2.cs           # OLE2(CFB) リーダ/ライタ（自前実装）
│   ├── 06_VbaCompression.cs # MS-OVBA 2.4.1 展開・圧縮（自前実装）
│   ├── 07_VbaProject.cs     # dir の MODULE レコードを正本とするモジュール一覧・コード取得・コードページ・書き戻し計画
│   └── 08_BookIO.cs         # xlsm/xlam/xlsb(zip) の入出力、コピー生成、ビルド、検証
├── assets/                  # UI 実体（日本語 OK）
│   ├── index.html
│   ├── css/  (variables / layout / steps / module-list / diff / lecture)
│   ├── js/   (app / state / host-bridge / diff / diff-report / diff-view /
│   │          vba-highlight / lecture / prompt-template)
│   └── messages/ (ホスト(C#)が表示する日本語文言 *.txt。src/ は ASCII のまま)
├── presets/                 # 改修マニュアル（*.md、1 ファイル = 1 ボタン）
├── templates/               # 依頼ファイル全体の編集可能なテンプレート

└── README.md

`testdata/` は git 管理外とし、開発機ローカルで検証用ブックを置く
（[DEVELOPMENT.md](DEVELOPMENT.md) 参照）。

### 2.5 対応ファイル形式

| 拡張子 | 中身 | v1 の扱い |
|---|---|---|
| `.xlsm` | zip 内 `xl/vbaProject.bin`（OLE2） | 対応 |
| `.xlam` | 同上 | 対応 |
| `.xls`  | ファイル全体が OLE2 | **v1 対象外**（添付時に E-ATTACH-01 の明示エラー） |
| `.xlsb` | zip 内 `xl/vbaProject.bin`（OLE2） | 対応予定。機構上は xlsm と同一経路で動くはずだが**未検証**（§15） |
| その他 | — | 添付時に「対応形式ではありません」 |

補足:
- VBA プロジェクトにパスワード保護が掛かったブック: 保護は VBE の閲覧ゲートであり
  モジュールストリーム自体は暗号化されない（MS-OVBA 仕様）ため、抽出・書き戻しとも
  影響を受けない**見込み**。実ファイルでの確認は未実施（§15）。

## 3. 画面構成

### 3.1 レイアウト

```
┌────────────────────────────────────────────────────────────┐
│  ① 添付 ──── ② 依頼作成 ──── ③ 取り込み ──── ④ ビルド      │ 進捗バー
├──────────────┬─────────────────────────────────────────────┤
│              │                                             │
│  モジュール   │                                             │
│  一覧         │        メイン画面（ステップで中身が変わる）    │
│  (左 1/4)     │        (右上 3/4)                            │
│              │                                             │
│  [バッジ付き] ├─────────────────────────────────────────────┤
│              │  レクチャー画面（右下・状況に応じた条件分岐）    │
└──────────────┴─────────────────────────────────────────────┘
```

- 上部: ①〜④ の進捗バー（Web アンケートフォーム風）。**戻れる**こと
  （③ で diff を見て「違う」となったら ② に戻って言い直す動線が必要）。
- 左カラム 1/4: モジュール一覧。**全ステップ通して常駐**。状態バッジ付き。
- 右上 3/4: メイン画面。文脈で中身が変わる。
- 右下 1/4: レクチャー画面。固定文ではなく**状況に応じた条件分岐**（§11）。

### 3.2 寸法と 1366x768 対応

想定最小解像度 1366x768（作業領域 高さ約 728px、100% スケール）。

| 領域 | 高さ/幅 |
|---|---|
| 進捗バー | 高さ 48px 固定 |
| 左カラム | 幅 25%（最小 220px）、縦フル |
| レクチャー欄 | **展開時 高さ 150px / 折り畳み時 28px（見出し行のみ）** |
| メイン画面 | 残り全部（1366x768 展開時で約 500px 確保） |

レクチャー欄は**畳める。既定は開いた状態**。
折り畳み状態はステップ遷移で維持し、エラー発生時のみ自動で開く（§11）。

### 3.3 モジュール一覧（左カラム）

- 表示順は VBE のプロジェクトツリーと同じ: ドキュメント → フォーム → 標準 → クラス、
  同種内は名前順。
- 1 行 = アイコン（種別）+ モジュール名 + 行数 + 状態バッジ。
- クリックで選択。③ではメイン画面がそのモジュールの diff / 貼り付け画面に切り替わる。
  ①②④では選択するとメイン画面にコードの読み取り専用プレビューを重ねて表示できる
  （「コードから離れない」原則。閉じると各ステップの本来の画面に戻る)。

状態バッジは §10.2 参照。
③では一覧末尾に、低い強調度で［新規モジュールとして取り込む］を置く。
返答に新しい標準モジュールがある場合だけ使用し、既存項目や主要操作とは競合させない。

### 3.4 ③のメイン画面（左右 diff）

- 左 = 現在のコード（読み取り専用）、右 = 貼り付け先。
- **右ペインはエディタの見た目だが手打ちできない。**
- 貼る前: 右ペイン中央に大きく **［Copilotの返答を貼り付ける］** ボタンだけが光る。
- 押すとクリップボードから流し込まれ、**その瞬間に左右 diff 表示になる**。
  Ctrl+V でも入る（両対応）。
- 貼り直しはいつでも可能（上書き）。［貼り付けを取り消す］で貼る前の状態に戻せる。
- 新規標準モジュールは名前を手入力してから同じクリップボード経路で取り込む。
  貼り付け内容から名前や種別を抽出・推測しない。取り消すと新規項目自体を一覧から除く。

diff 描画は自前実装（Monaco 不使用）。§13.1 参照。

### 3.5 グロー原則の適用

各状態で「光る」のは次の 1 個（詳細は §5・§10）:

| 状態 | 光るもの |
|---|---|
| ① 添付前 | ドロップゾーン（＝ファイル選択ボタン兼用） |
| ① 添付後 | ［次へ（依頼を作る）］ |
| ② 依頼文が空 | プリセットボタン |
| ② 依頼文あり | ［依頼ファイルを作成］ |
| ② 作成済み | ［次へ（返答を取り込む）］ |
| ③ モジュール未選択 | モジュール一覧の先頭の未処理項目 |
| ③ 選択済み・未貼り付け | ［Copilotの返答を貼り付ける］ |
| ③ 1 件以上確定 | 次の未処理モジュール（一覧側）。同時に ④ タブが点灯 |
| ③ 新規モジュール取り込み | ［新規モジュールとして取り込む］ |
| ④ | ［ビルド］ |
| ④ 成功後 | ［出力フォルダを開く］ |

## 4. ワークフロー（4 ステップ）

1. **対象ファイル添付** — xlsm 等を D&D → VBA プロジェクトを抽出、モジュール一覧を表示。
2. **プロンプト生成** — 改修依頼を入力（プリセットボタンでマニュアル本文が流し込まれる）
   → ソースコード込みの依頼テキストファイルを出力 → エクスプローラでそのファイルを
   選択した状態で開く → 使用者が Copilot Chat に添付。
3. **diff 貼り付け・確認** — Copilot がモジュール単位で全文を返す。使用者はモジュール
   一覧から対象を選び、［Copilotの返答を貼り付ける］でクリップボードから流し込む
   → 左右 diff。新しい標準モジュールは名前を入力して取り込む。直したモジュールの
   数だけ繰り返す。
4. **ビルド** — xlsm に書き戻す（別名保存）。

## 5. ステップ別詳細仕様

### 5.1 ① 対象ファイル添付

メイン画面: 大きなドロップゾーン + 「ファイルを選ぶ」ボタン（同じ動作の保険経路）。

処理フロー:

1. D&D またはファイル選択でパスを受け取る（D&D の実装方式は §7.4）。
2. 拡張子チェック（§2.5）→ 非対応なら E-ATTACH-01。
3. エンジンでブックを読み込む（コピーをメモリに読むだけ。元ファイルはロックしない。
   読み込み後にファイルハンドルを保持しない）。
4. 成功: メイン画面にブック情報カード（ファイル名 / モジュール数 / 合計行数）を表示し、
   左カラムにモジュール一覧（全部「未処理」バッジ）を表示。［次へ］が光る。
5. 失敗: §12 のエラー分岐。

別ブックの添付し直し: ① に戻っていつでも可能。ただし貼り付け済みモジュールが
1 件でもあれば確認ダイアログ（「取り込み済みの内容が破棄されます」）→ OK で全状態リセット。

### 5.2 ② プロンプト生成

メイン画面の構成（上から）:

1. **依頼文入力欄**（自由編集可のテキストエリア。ここだけが編集可能）
2. **プリセットボタン列** — `presets/*.md` の 1 ファイルにつき 1 ボタンを自動生成
   。ボタン名はファイル名（拡張子抜き）。押すと、そのファイルの本文が
   依頼文入力欄の**末尾に追記**される（入力欄が空なら本文そのものになる）。
   流し込み後も自由に編集できる。presets/ が空 or 無い場合はボタン列自体を出さない。
3. **依頼テンプレートの案内** — `templates\request-template.txt` が依頼ファイル全体の
   正本であり、内容を変える場合は同ファイルを編集する旨を折り畳み表示（既定は閉）。
   実際の生成内容と食い違う固定文プレビューは表示しない。
4. **［依頼ファイルを作成］ボタン**（グロー対象）

［依頼ファイルを作成］の動作:

1. `templates\request-template.txt` を strict UTF-8 で読み直し、§6 の変数を検証して
   依頼テキストを組み立てる。読み込みまたは検証に失敗した場合は E-GEN-02 で中止する。
2. **対象ブックと同じフォルダ**に `<ブック名（拡張子抜き）>_改修依頼_<yyyyMMdd_HHmmss>.txt`
   として保存（UTF-8 BOM 付き）。日時入りのため上書きは起きない。
3. `explorer.exe /select,"<保存パス>"` でそのファイルを選択した状態でエクスプローラを開く。
4. メイン画面に「作成済み: <ファイル名>」と Copilot Chat への添付手順を表示。
   ［もう一度作成する］（依頼文を直した場合用）と［次へ］を表示。

依頼文が空のまま［依頼ファイルを作成］を押した場合: 作成は許可する（マニュアル無しの
自由依頼もあり得るため）が、空文字列のときのみ「依頼が空です」トーストで止める。

### 5.3 ③ diff 貼り付け・確認

前提: ブック添付済みであること（②の依頼ファイル作成は前提にしない。
過去に作った依頼の返答を持って来る使い方を許す）。

画面フロー:

1. モジュール未選択時: メイン画面に「左の一覧から、Copilot の返答にあるモジュールを
   選んでください」の案内。レクチャー欄が返答サマリーの読み方を説明（L3-1）。
2. モジュール選択時（未貼り付け）: 左ペインに現在のコード（読み取り専用・
   シンタックスハイライト付き）、右ペイン中央に［Copilotの返答を貼り付ける］ボタン。
3. 貼り付け（ボタン押下 or Ctrl+V）:
   - クリップボードのテキストを取得（C# 側 `Clipboard.GetText()`。§7.3）。
   - §8 の正規化を適用。正規化後が空なら E-PASTE-01（状態は変えない）。
   - モジュール状態を**確定**にし、左右 diff を表示（§13.1）。
   - 正規化後のテキストが現在のコードと同一なら、確定にはするが
     「変更なし」扱い（バッジ表記・ビルド対象外。L3-4 で案内）。
4. diff 表示中: ［貼り付けを取り消す］［貼り直す（クリップボードから再取り込み）］を
   小さく表示。モジュール一覧で別モジュールを選べば切り替わる（状態は保持）。
5. 直したモジュールの数だけ 2〜4 を繰り返す。
6. 新しい標準モジュールの場合は一覧末尾の［新規モジュールとして取り込む］を押し、
   31 文字以内の VBA 識別子を名前として入力してコードブロックを取り込む。
   種別は標準モジュール固定。既存名との重複は受け付けない。
7. 「違う」となったら進捗バーで ② に戻り依頼を言い直す。②〜③の往復では
   貼り付け済み状態を**保持**する（言い直しは大抵 1 モジュールだけのため）。
   ①でブックを替えたときだけ全リセット。

補足: 既定テンプレートの指示（変更したモジュールのみ出力）にもかかわらず Copilot が
無関係なモジュールを余計に返してきた場合も、使用者がそのモジュールを選んで
貼らない限りブックには反映されない。この「選ばなければ何も起きない」構造を
設計上の安全弁とし、ツール側に余計な返答の検出・除外ロジックは**足さない**。

### 5.4 ④ ビルド

画面フロー:

1. **確認画面**: 書き戻し対象（確定かつ変更ありのモジュール）の一覧と変更行数、
   出力ファイル名（`<ブック名>_改修済_<yyyyMMdd_HHmmss><元の拡張子>`）を表示。
   未処理・対象外・変更なしの件数も添える。［ビルド］が光る。
2. **実行**: §9 の手順。実行中はプログレス表示（通常 1〜2 秒想定）。
3. **成功画面**: 出力パス表示 + ［出力フォルダを開く］（explorer /select）。
   「Excel で開いてマクロの動作を確認してください」の案内（L4-2）。
   モジュール一覧の書き戻し済みモジュールに「書込済」バッジ。出力フォルダで
   explorer が選択するのは改修済みブックのまま維持する。
4. **失敗画面**: モジュール別の結果表（§9.4）。出力ファイルは残さない。
   レクチャー欄に復帰手順（§12）。

ビルドは**元ファイルを上書きせず別名保存**。
ビルド成功後、同じフォルダへ
`<ブック名>_改修差分_<yyyyMMdd_HHmmss>.html` も `FileMode.CreateNew` で出力する。
改修済みブックと同じタイムスタンプを使い、今回書き戻した全モジュール
（新規標準モジュールを含む）の左右差分を 1 ファイルにまとめる。
HTML はインライン CSS のみを持つ自己完結ファイルとし、差分計算は画面と同じ
`assets/js/diff.js` を使う。HTML の生成・書き込みだけが失敗した場合はログと
エラートーストに通知するが、完成済みブックの成功は取り消さない。
④ の後も ③② に戻って続きの改修 → 再ビルドできる（出力はその都度新しい日時名）。

## 6. 依頼ファイル（プロンプト）形式

### 6.1 全体構造

依頼ファイルは `templates\request-template.txt` を正本として生成するプレーンテキスト。
出力ファイルは UTF-8 BOM 付き、改行は CRLF、末尾は CRLF 1 個とする。同梱する既定
テンプレートは次の 5 部構成だが、使用者はテンプレートを編集して構成と AI への指示を
変更できる。

```
(a) 冒頭の説明 1 段落（このファイルが何か）
(b) 【依頼】     … 依頼文入力欄の内容そのまま
(c) 【対象ブック】… ファイル名・モジュール一覧（種別・行数）
(d) 【ソースコード】… 全モジュールの全文（Attribute 行除去済み）
(e) 【出力形式の指定】… AI に求める返答形式
```

設計上の確定事項:

- `{{MODULE_SOURCE_BLOCKS}}` は**常に全モジュール**を含める。載せるモジュールを
  絞り込む・選択する UI は作らない（使用者に「どれを載せるか」を判断させない）。
- ファイル添付方式のため、サイズ上限を理由としたプロンプト分割・バッチ送信の設計は
  入れない。
- ② の出口は「ファイル出力 + explorer /select」の一本に絞る。
  「テキストをコピー」等の別経路は置かない（§14 とも整合）。

### 6.2 外部テンプレートと差し込み変数

［依頼ファイルを作成］を押すたびに `templates\request-template.txt` を strict UTF-8
で読み直す。起動後に編集した内容も次回生成へ反映する。ファイルが無い、読み取れない、
UTF-8 として不正、または変数が不正な場合は E-GEN-02 で中止し、内蔵文面などへ
fallback しない。

| 変数 | 必須 | 差し込む値 |
|---|---|---|
| `{{REQUEST_TEXT}}` | 必須 | 依頼文入力欄の内容 |
| `{{BOOK_NAME}}` | 任意 | 対象ブックのファイル名（ディレクトリを含まない） |
| `{{MODULE_COUNT}}` | 任意 | モジュール数 |
| `{{TOTAL_LINE_COUNT}}` | 任意 | 全モジュールの合計行数 |
| `{{MODULE_LIST}}` | 任意 | `- 名前（種別, 行数）` 形式に整形した全モジュール一覧 |
| `{{MODULE_SOURCE_BLOCKS}}` | 必須 | 各モジュールの `■ 名前（種別）` 見出し、区切り線、Attribute ヘッダ除去済みの全文。空モジュールには「このモジュールは現在空です。コードの省略ではありません」という注記を含む |

`{{REQUEST_TEXT}}` と `{{MODULE_SOURCE_BLOCKS}}` はそれぞれ 1 回以上必要。任意変数は
省略でき、既知変数は複数回使える。未知の `{{NAME}}` または壊れた変数表記は
E-GEN-02 とする。値は文字列として改行だけを CRLF へ正規化して差し込み、内容の
解釈・エスケープ・代替値への置換は行わない。差し込んだ値の中にある `{{NAME}}` 形式の
文字列も変数として再解釈しない。変数値末尾とテンプレート側直後の改行は重複分を
重ね合わせ、値が末尾改行を持つ場合もテンプレートで定めた段落境界を保つ。

空モジュール注記は `{{MODULE_SOURCE_BLOCKS}}` の値に含まれるため、同変数を通常どおり
使う限り省略されない。この変数を使わない別の生成経路や、生成後の編集で注記を落とすと、
空モジュールを「コードの省略」と誤認させないための保護も失われる。その変更を行うかは
利用者の裁量だが、MacroDesk のテンプレートから同変数を外した場合は必須変数検証により
E-GEN-02 で停止する。

モジュール種別の表記: 標準モジュール / クラスモジュール / フォームモジュール /
ドキュメントモジュール。

### 6.3 同梱する既定テンプレート

同梱する `templates\request-template.txt` が既定文面の単一定義である。C# または JS に
同じ文面を fallback として持たない。既定テンプレートは、改修サマリー、変更した
モジュールだけのコード全文、空モジュール注記の扱い、Attribute 行の扱い、新規標準
モジュールの見出し、削除・名前変更の禁止を AI へ指示する。

使用者はこのファイルを直接編集して、構成や AI への指示を変更できる。Step 2 は実内容の
固定プレビューを持たず、編集場所だけを案内する。既定ファイルを使った生成結果は、
外部化前の既定文面と byte 単位で一致することを回帰テストで保証する。

補足:
- 既定テンプレートは「■ モジュール名」の見出し形式を依頼側と返答側で揃え、
  Copilot が同じ形式で返しやすくする。
- 使用者がチャットに打つ文言（例:「添付ファイルの依頼に従ってください」）は
  レクチャー欄 L2-3 で案内する。ツールは Copilot 側の操作には関与しない。

### 6.4 Attribute 行の扱い

- 抽出時: 各モジュール**先頭の連続した** `Attribute VB_*` 行群（ヘッダブロック）を
  分離して保持し、画面表示・依頼ファイルには**含めない**（VBE でも見えない行であり、
  使用者と Copilot の双方にノイズのため）。コード途中のプロシージャ属性
  （`Attribute xxx.VB_UserMemId` 等。稀）はコードの一部としてそのまま残す。
- 既定テンプレートで Copilot にも「先頭に Attribute 行を付けない」よう指示（§6.3）。
- 貼り付け時: 万一先頭に含まれていても機械的に除去（§8。先頭ブロックのみ。
  抽出時と同じ規則にすることで、コード途中の属性を巻き添えにしない）。
- ビルド時: 保持しておいた**元のヘッダをそのまま先頭に再付与**して書き戻す。
  `Attribute VB_PredeclaredId` 等の意味を持つ属性が失われることを防ぐ。
- 新規標準モジュールだけは、C# 側で `Attribute VB_Name` を生成する。
- 帰結として既存モジュールの Attribute 行は変更できない（用途上不要。§14）。

## 7. データの流れとプロセス構成

### 7.1 全体像

```
使用者
 │ D&D / クリック
 ▼
WebView2 (HTML/JS)  ←― assets/ を https://macrodesk.local/ にマッピング
 │  window.chrome.webview.postMessage({id, action, params})
 ▼
C# ホスト (WPF, STA スレッド)
 │  03_MessageRouter が action を分岐
 ├─ 04_HostServices … ダイアログ / クリップボード / explorer / 依頼ファイル / template / presets / ログ
 └─ 05〜08 エンジン … ブック読込・ビルド（メモリ内 byte[] 操作）
 │  PostWebMessageAsJson({id, status, data} または {event, data})
 ▼
WebView2 (JS)  … host-bridge.js が id で Promise 解決
```

- IPC は id 付き request/response + event push 方式。JSON は
  `System.Web.Script.Serialization.JavaScriptSerializer`（`MaxJsonLength = int.MaxValue`）。
- エンジン呼び出しはワーカースレッド（`Task.Run`）で実行し UI を固めない。
  応答は同じ id で返す。

### 7.2 IPC アクション一覧

| action | params | 応答 data | 備考 |
|---|---|---|---|
| `getAppInfo` | — | `{version, presets:[{name,file}]}` | 起動時に JS が取得 |
| `pickBook` | — | `{path}` / `null` | OpenFileDialog（フィルタは §2.5） |
| `attachBook` | `{path}` | `{book:{path,name,ext,totalLines}, modules:[{name,type,typeLabel,ext,lineCount,code,attributes}]}` | code は先頭 Attribute ブロック除去済み。attributes は除去した元ヘッダ（ビルド時の再付与用に JS が保持）。失敗時 `{status:"error", code, message}` |
| `readPreset` | `{file}` | `{content}` | presets/ 内のみ許可 |
| `readRequestTemplate` | — | `{content}` | `templates\request-template.txt` を生成のたびに strict UTF-8 で読む。失敗時 E-GEN-02 |
| `writeRequestFile` | `{content}` | `{path}` | 命名・保存先・/select は §5.2。ブックは attach 済み前提 |
| `readClipboard` | — | `{text}` | 空なら `{text:""}` |
| `buildBook` | `{outputTimestamp, modules:[{name, code, isNew?}], diffHtml}` | `{outputPath, results:[{name, result, message}], diffPath?, diffError?}` | 既存 code は Attribute 再付与済み。新規は `isNew:true` と可視コードを渡し、C# 側で標準モジュールの Attribute を生成。HTML 出力失敗時もブックは成功。§5.4, §9 |
| `revealPath` | `{path}` | — | explorer /select |
| `writeLog` | `{level, message}` | — | UI 側の要所ログ |

イベント push（C#→JS、id なし）: `bookDropped {path}`（D&D 受領時）。

### 7.3 クリップボード

- 取得は C# 側 `System.Windows.Clipboard.GetText()`（STA スレッド上で実行）。
  ブラウザの clipboard permission ダイアログを出さないための方式。
- Ctrl+V は JS の `paste` イベントで受け、`clipboardData.getData('text')` を使う
  （paste イベント内は許可不要）。ボタン経路とイベント経路で同じ正規化・
  同じ処理関数に合流させる。

### 7.4 ドラッグ＆ドロップ

WebView2 の HTML 側 D&D では**ファイルのフルパスが取れない**（ブラウザの
サンドボックス仕様）ため、次の優先順で実装する。

1. **方式A（第一候補）**: `CoreWebView2Controller.AllowExternalDrop = false` を設定し、
   WPF 側（Window / WebView2 要素の親）の `AllowDrop=true` + `Drop` イベントで
   `DataFormats.FileDrop` からパスを得る。得たパスを `bookDropped` イベントで JS へ。
2. **方式B（フォールバック）**: JS 側 drop で
   `chrome.webview.postMessageWithAdditionalObjects()` を使い、C# 側で
   `e.AdditionalObjects` の `CoreWebView2File.Path` を読む（SDK 1.0.3856.49 は対応版）。
3. **方式C（常設の保険）**: 「ファイルを選ぶ」ボタン（OpenFileDialog）。

実装では**方式A が成立したため方式A を採用**している。方式C は常設の保険として
残しており、D&D が使えない環境でも機能は成立する。

### 7.5 ログ

- 出力先: `%LOCALAPPDATA%\MacroDesk\logs\macrodesk_<yyyyMMdd>.log`（追記、UTF-8）。
- 書式: `[HH:mm:ss] [LEVEL] message`。
- 記録する事象: 起動/終了、attach（パス・モジュール数）、依頼ファイル生成（パス）、
  貼り付け（モジュール名・行数のみ。**コード本文は記録しない**）、ビルド開始/結果、
  すべてのエラー（スタック含む）。

## 8. 貼り付けテキストの正規化

貼り付け時に次の規則を**この順で**機械的に適用する。これは §1.2 の「帳簿付け」であり、
ここに列挙した以外の加工をしてはならない。

1. 改行を CRLF に正規化する。
2. 行頭が ``` で始まる行（コードフェンス）を削除する
   （Copilot のコピーボタンではなく手動範囲選択でコピーした場合の保険）。
3. **先頭から連続する** `Attribute VB_` 行（大文字小文字無視、行頭空白許容。
   間の空行は許容して読み飛ばす）を削除する（§6.4 と同じ「先頭ブロックのみ」規則。
   コード途中の Attribute 行には触れない）。
4. 先頭・末尾の空行を除去し、末尾に CRLF を 1 つ確保する。

正規化の結果はそのまま右ペイン・diff に出る（使用者から見て隠れた加工にしない）。
正規化後が空文字列なら貼り付け不成立（E-PASTE-01）。

ビルド直前の結合（JS 側）: 既存モジュールは
`保持していた Attribute ヘッダ + CRLF + 正規化済みテキスト` を最終コードとして渡す。
新規標準モジュールは可視コードと `isNew:true` を渡し、C# 側で `VB_Name` を生成する。

## 9. ビルド仕様（書き戻しエンジン）

### 9.1 手順

1. 元ブックを出力名（§5.4）でコピーする。**元ファイルには一切触れない**。
2. コピーから vbaProject.bin（zip エントリ）を取り出し、OLE2 として読み込み、
   **全エントリの論理情報と全ストリーム内容をメモリに展開**する。
3. 書き戻し対象モジュール（確定かつ変更あり）ごとに、新しいストリーム内容を作る:
   - 既存モジュールは、最終コード（Attribute 付き）をプロジェクトのコードページで
     encode → MS-OVBA 圧縮する。モジュールストリームの先頭
     `[0, SourceOffset)`（PerformanceCache 部）は
     そのまま温存し、`SourceOffset` 以降を新しい圧縮データに差し替える。
     **SourceOffset は dir の MODULEOFFSET を正本**とし、書き戻し対象ストリームは
     **dir の MODULESTREAMNAME で対応付ける**。
   - 新規標準モジュールは `Attribute VB_Name` と可視コードの全文を圧縮し、
     PerformanceCache なし（`MODULEOFFSET=0`）の新規ストリームにする。
     dir の `PROJECTMODULES` と MODULE レコード、PROJECT の `Module=` 行、
     PROJECTwm の NAMEMAP を同じ順序で追加する。
4. **OLE2 複合ドキュメントを丸ごと再構築する（§9.2。唯一の書き込み経路）**:
   全エントリ（差し替えたストリームと新規モジュールストリームを含む）を
   新しいコンテナとして直列化する。
5. 再構築した vbaProject.bin をコピー先ブックに書き戻す（zip の該当エントリを
   Update モードで書き換え）。
6. **検証（必須手順）**: コピー先ブックをエンジンで読み直し、次の 3 点を確認する。
   - (a) 書き戻した全モジュールの展開後テキストが、渡した最終コードと一致
     （CRLF 正規化後の完全一致）
   - (b) 新規追加時に更新する dir / PROJECT / PROJECTwm と新規ストリームを除き、
     **それ以外の全ストリームが元の内容と byte 単位で一致**
   - (c) ストレージ/ストリームの木構造・名前・種別・CLSID・state bits が
     維持されている
7. 1 つでも失敗（検証・I/O）したら**出力ファイルを削除**し、モジュール別の結果を
   返す（**all-or-nothing**。中途半端に直ったブックを現場に残さない）。

### 9.2 全面再構築方式

**なぜ全面再構築か**: 既存セクタチェーンへ in-place で書き込む方式
（+ パディング + リロケートの 3 段配置規則）は、本ツールの用途では成立しない。
実測では、典型的な改修として 1 行追加しただけで、検証した全モジュール
（18/18。すべて mini ストリーム、スラック 0〜41B に対し圧縮後の増分 55〜75B）が
in-place 不能だった。「コードが増える」のが常態である以上、
**全面再構築を唯一の書き込み経路**とする。

**方式**: コンテナ（MS-CFB）水準の再構築。

- **保持する論理情報**（元から機械的に移送）: ストレージ/ストリームの木構造（親子）、
  名前、種別、CLSID、state bits、作成/更新時刻、全ストリーム内容。
  モジュールストリーム以外のストリーム（`_VBA_PROJECT` / `dir` / `__SRP_*` /
  `PROJECT` / `PROJECTwm` 等）は、既存モジュールだけの変更では
  **内容を解釈せず、不透明な byte 列としてコピー**する。新規追加時だけ、
  dir / PROJECT / PROJECTwm に規定のレコードを追加する。
- **毎回新規に決めるもの**（物理配置。MS-CFB 上、意味を持たない）: セクタ番号、
  チェーン順序、空きセクタ、FAT / DIFAT / miniFAT の中身。
- mini / 通常ストリームの所属は、再構築時に各ストリームのサイズ（cutoff 4096）から
  自然に決まる。**パディングは不要**。
- ディレクトリの兄弟赤黒木は MS-CFB の名前順（長さ → 大文字化比較）で構築する。
- 出力は v3（512B セクタ）で直列化する。v4（4096B セクタ）の入力は実務上ほぼ無い
  想定で、遭遇した場合は明示エラーにする（未検証事項として記録）。
- 出力ファイルのバイト配置は元と変わる（空きセクタが落ちるため通常は小さくなる）が、
  意味的な差はない。
- 署名: VBA プロジェクト署名は vbaProject.bin の外の別パート
  （`xl/vbaProjectSignature.bin` 等）にあり、モジュールを書き換えた時点でどの書き込み
  方式でも無効になる。再構築固有の不利ではない。v1 は署名パートに触れない。

**品質保証（必須。すべて満たすまでリリースしない）**:

1. **ラウンドトリップ試験**: 無変更で再構築 → 全ストリーム byte 一致・木構造等の
   論理情報一致（開発時の常設テスト。毎ビルドが同じ経路を通るため、この試験が
   本番経路そのものを検証する）。
2. **ビルド後の読み直し検証**（§9.1-6。全ストリーム対象）。
3. **Excel 実機確認**（再構築した出力を Excel で開き、マクロ動作を確認する。
   リリース前の手動確認項目）。

### 9.3 書き戻しが変更しないもの

- 既存モジュールの PerformanceCache（各モジュールストリームの先頭部）、
  `_VBA_PROJECT` / `__SRP_*` 等の他ストリーム: **内容を一切変更しない**
  （再構築で物理配置は変わるが、内容は byte 単位で維持され、§9.1-6(b) で検証される）。
  既存ソースの差し替えと新規標準モジュールの追加だけを行い、再コンパイルは Excel 側に任せる。
- dir / PROJECT / PROJECTwm は新規追加時だけ必要なレコードを追記し、
  それ以外の既存 byte 列を維持する。
- zip 内の vbaProject.bin 以外のエントリ（シートデータ等）: 触れない。

### 9.4 モジュール別結果コード

| result | 意味 | all-or-nothing 後の扱い |
|---|---|---|
| `written` | 書き込み・検証 OK | 成功時のみ |
| `verify_failed` | 読み直し検証で不一致 | 全体失敗（出力破棄） |
| `io_error` | コピー/zip 書き込み失敗 | 全体失敗 |
| `skipped_no_change` | 変更なしのため書き込み対象外 | 情報表示のみ |

再構築処理そのものの内部エラーは、モジュール別ではなくビルド全体のエラーとして
扱う（E-BUILD-01。出力は残さない）。

## 10. 状態遷移

### 10.1 アプリ状態

```
[起動] → ①(未添付) ─attach成功→ ①(添付済み) ─次へ→ ② ⇄ ③ ⇄ ④
                                      ▲                     │ビルド成功
                                      └──①で別ブック添付────[完了画面]─続けて改修→③
                                         （確認→全リセット）  └別ブックへ→①(未添付)
```

進捗バーの遷移可否:

| 現在地 | ①へ | ②へ | ③へ | ④へ |
|---|---|---|---|---|
| ①未添付 | — | 不可 | 不可 | 不可 |
| ①添付済み | — | 可 | 可 | 確定(変更あり)≥1 なら可 |
| ② | 可 | — | 可 | 同上 |
| ③ | 可 | 可 | — | 同上 |
| ④ | 可 | 可 | 可 | — |

「①へ」= ブック差し替え動作。貼り付け済みが 1 件でもあれば確認ダイアログ（§5.1）。
②⇄③⇄④ の往復では全状態を保持する（§5.3-6）。

### 10.2 モジュール状態とバッジ

「全部グレーで始めて、貼ったものが確定になるだけ」を基本に、
次の 4 状態 + 新規表示 + 書込済表示とする。

```
未処理 ──貼り付け──▶ 確定（変更あり）──取り消し──▶ 未処理
  │  ▲                確定（変更なし）〔貼った内容が現在と同一の場合〕
  │  └─解除───┐
  └─手動指定─▶ 対象外
（ビルド成功後、書き戻したモジュールに追加表示: 書込済）
新規取り込み ──▶ 新規（変更あり）──取り消し──▶ 一覧から削除
```

| バッジ | 表示 | 色 | 誰が付けるか |
|---|---|---|---|
| 未処理 | `未` | グレー #808080 | 初期状態（ツールは対象を事前に知らない） |
| 確定（変更あり） | `確` + 変更行数 | 緑 #6a9955 | **貼り付けた事実**によって自動 |
| 新規（変更あり） | `新` | 青 #3977a8 | 新規標準モジュールとして取り込んだ事実によって自動 |
| 確定（変更なし） | `同` | 薄緑（半透明） | 貼った内容が現在コードと同一のとき自動 |
| 対象外 | `外`（名前は打ち消し気味） | 薄グレー | **使用者が手動**（右クリック or バッジクリック） |
| 書込済 | `済` | 青系 #4f9cd8 | ビルド成功の事実によって自動 |

- 「対象外」は Copilot のサマリーに「変更なし」とされたモジュール等を、使用者が
  自分のチェックリストとして消し込むための**任意の手動マーク**。ビルド動作には
  影響しない（どのみち書き戻すのは確定・変更ありのみ）。
- ツールが Copilot の返答から対象モジュールを推定してバッジを付けることは
  **しない**（§1.2）。代わりにレクチャー欄 L3-5 で「サマリーの箇条書きと確定バッジの
  数を照合してください」と人間側の照合を促す。
- 色は diff の配色（modified 橙 / added 緑 / removed 赤 / unchanged 灰）と
  世界観を揃える。

## 11. レクチャー欄の条件分岐一覧

- 実装は `assets/js/lecture.js` に「条件 → 表示内容」の分岐表として集約する。
  分岐キーは（ステップ, サブ状態, 直近エラー）。

| ID | 条件 | 要旨 |
|---|---|---|
| L1-1 | ①・未添付 | 対応形式（xlsm 等）と「ここにドラッグ」。Excel で開いたままのファイルは添付できないこと |

| L2-1 | ②・依頼文空 | プリセットボタンの説明（マニュアル本文が入るだけで、編集して良い）。自分の言葉で書き足して良いこと |
| L2-2 | ②・依頼文あり・未作成 | ［依頼ファイルを作成］で何が起きるか（ブックと同じフォルダに txt、エクスプローラが開く） |
| L2-3 | ②・作成済み | **Copilot Chat 側の操作手順**: 開いたエクスプローラのファイルをチャットに添付 →「添付ファイルの依頼に従ってください」と送信 → 返ってきたら ③ へ |

| L3-3 | ③・diff 表示中（変更あり） | diff の見方（左=今、右=貼った内容。赤=消える行、緑=増える行）。意図どおりなら残りを取り込むか ④ へ進む。違えば ② に戻って言い直すか、貼り付けを取り消す |
| L3-4 | ③・diff 表示中（変更なし） | 貼った内容が現在のコードと同一。別モジュールのコードをコピーした可能性。サマリーを確認 |

| L4-2 | ④・成功 | 次にやること: ［出力フォルダを開く］→ Excel で開く → マクロを実際に動かして確認。問題があれば元ファイルで ① からやり直せる |

## 13. 検討論点への回答

### 13.1 diff 表示: Monaco は使わない → 自前 diff 描画の設計

Monaco Editor は**使わない**。diff は MacroDesk 自身の JS 実装とする。

| 部位 | 実装先 |
|---|---|
| 貪欲法の行 diff（先読み窓 100 行、changed ペアリング） | `assets/js/diff.js` |
| 左右比較テーブルの構造と配色（equal/changed/removed/added、行番号列、中央セパレータ、ダークテーマ） | `assets/js/diff-view.js` + `assets/css/diff.css` |
| ビルド後の自己完結 HTML（全変更モジュールの左右比較） | `assets/js/diff-report.js`（計算は `diff.js` を直接利用） |

追加設計（③ の要件への適合）:

- 右ペインは**貼り付け前はボタンのみ、貼り付け後は diff の右列**になる。
  手打ち編集は要件上存在しないため、エディタエンジンは不要で、読み取り専用の
  「エディタの見た目」（等幅フォント・行番号・ダーク配色）を diff テーブルで実現する。
- シンタックスハイライト: 軽量な行単位トークナイザ（コメント / 文字列 / キーワード /
  数値の 4 分類程度）を `assets/js/vba-highlight.js` として自前実装する。
  equal 行に適用し、changed/added/removed 行は diff 背景色を優先。
- 行内（単語レベル）の変更強調: changed ペア行内の共通接頭辞・接尾辞を除いた
  差分範囲を下線+濃色で示す（任意の磨き込み項目）。
- 大きいモジュール対策: 5,000 行超は変更ブロック周辺 ±10 行に折り畳む
  「変更箇所のみ表示」トグルを付ける（既定 OFF = 全文表示）。

### 13.2 状態バッジは誰が付けるか

§10.2 のとおり「全部グレー → 貼ったものが確定」を基本とし、
「事実由来のバッジは自動、意図由来のバッジ（対象外）だけ手動」という整理を加えた。
自動バッジはすべて「使用者がした操作」または「ビルドの結果」という**ツール内で
確定している事実**から導かれ、Copilot の返答解釈を一切必要としない。

### 13.3 新規モジュール追加を v1 に含めるか（結論: 標準モジュールのみ含める）

- 共通処理を既存モジュールへ重複して置かず、新しい標準モジュールへ分離できる。
- 使用者が名前を入力して明示的に取り込む。返答から名前や種別を自動抽出しない。
- OLE2 の新規ストリーム、dir の MODULE レコード、PROJECT の `Module=` 行、
  PROJECTwm の NAMEMAP を一括して追加し、§9.1 の読み直し検証を通す。
- クラス、UserForm、ドキュメントモジュールの新規追加と、削除・名前変更は対象外。

### 13.4 利用者の習熟度に応じたモード分けを v1 に含めるか（結論: 含めない）

- 一本道フロー + レクチャー欄が、そのまま不慣れな利用者向けの体験になっている。
  慣れた利用者が欲しがる自由度（依頼文の自由編集、プリセット複数、レクチャー折り畳み、
  全モジュールのコード閲覧）は、**モードを分けなくても既に v1 の中にある**。
- モード切替 UI は「自分はどちらか」という迷いどころを増やし、§1.3 の原則に反する。
  文言・テストの二重管理コストも v1 の価値に見合わない。
- 将来、上級者向け機能（一括処理・解析系など）が実際に必要になったら、`settings.json` の
  フラグで**画面に切替を出さずに**追加する方式を推奨（付録 A）。

## 15. 既知の制限・未検証事項

v1 時点で「動くと確認できていること」と「まだ確認できていないこと」を分けて記す。
不具合の一覧ではなく、どこまで検証済みかの範囲表である。

### 15.1 実機で確認済み

- `.xlsm` の抽出・書き戻し・Excel での再オープンとマクロ実行。
- 無変更での再構築による全ストリームの byte 一致（ラウンドトリップ試験）。
- サイズの増減（+50% / +500% / 大幅削減 / mini↔通常ストリーム境界の跨ぎ）。
- DIFAT 継続（ヘッダの 109 参照を超える FAT）を持つ合成 fixture の読み・再構築。
- 複数モジュールの同時変更と all-or-nothing の失敗時挙動。
- 新規標準モジュールの追加、dir / PROJECT / PROJECTwm / 新規ストリームの再読検証、
  Excel での再オープンと追加マクロの実行。

### 15.2 未検証・限定的な範囲

1. **`.xlsb`**: 実ファイルの fixture を用意できていないため、best-effort 経路は
   実機未検証。解析に失敗した場合は E-ATTACH-05 の明示エラーになる。
2. **パスワード保護された VBA プロジェクト**: 仕様上は影響を受けない見込み（§2.5）だが、
   実ファイルでの確認は未実施。
3. **`.xlam`**: 合成 ZIP による経路の試験であり、Excel が実際に生成した fixture では
   検証していない。
4. **v4（4096B セクタ）の CFB 入力**: 読み取りは可能だが、書き出しは v3 のみ。
   v4 入力の再構築要求は明示エラーになる。実ファイルでの遭遇例は未確認。
5. **起動時ネイティブエラーのログ副作用**: WebView2 ランタイム不在時の MessageBox 経路は
   実機確認済み。その後に追加した起動エラーの best-effort ログ出力は、コンパイル確認
   のみで、ランタイム不在を再現しての実測はしていない。
6. **配布形態の E2E**: 別ディレクトリへ配置した状態からの `launch.vbs` 起動・ウィンドウ表示・
   コンソール非表示・ログ出力・終了は実プロセスで確認済み。ただしステップ ①〜④ の
   通し確認は、同じ配置物から起動した検証用 harness で行っており、先に起動した
   実プロセスを UI 自動操作したものではない。

### 15.3 実装済みだが未着手の整理

- 実装完了後のリファクタリングは未実施。動作と試験結果を優先し、構造の整理は
  後回しにしている。
