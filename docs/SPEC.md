# MacroStudio 仕様書（beta 1.0.0）

## 1. 目的と中核思想

### 1.1 目的

**マクロの改修が必要なのに、VBA に熟達した人が身近にいない。** MacroStudio は
その場面のためのツールである。マクロの中身の確認・診断・改修を、VBE を開かずに
チャット AI とのやり取りだけで進められるようにする。

判断はチャット AI が行う。MacroStudio は判断材料を運び、返ってきた結果を検証して
安全にブックへ書き戻す配管に徹する（§1.2）。

読み込んだマクロに対して選べるのは次の 2 つで、ブックを書き換えるのは
「改修する」だけである。どちらの側にも、同梱のひな形・利用者が足したひな形・
自由入力のひな形を置ける。

| 用途 | すること | 終わり方 |
|---|---|---|
| 改修する | AI の返答を取り込み、改修済みブックを作る | 改修済みブック・差分レポート・改修メモ |
| 診断する（AI に聞く） | 動くかの診断、進め方の相談、自由な質問 | AI へ渡す依頼文とコード全文 |

元のブックはどの用途でも変更しない。改修結果は必ず別名の新しいブックとして
専用フォルダへ作る（§5.4）。

### 1.2 中核思想

**ツールは判断を持たない。** 判断はすべてチャット AI に外部化し、ツールは判断材料を
運ぶ配管に徹する。

- `presets\*.md` の「ひな形」は検出ルールやコード置換規則では**ない**。1 ファイルが
  1 つの依頼の正本であり、プリセット名（H1）・改修指示・出力指示をその 1 枚に持つ。
  ツールは中身を解釈せず、見出しで切り分けて依頼文へ運ぶだけ（§5.2.1）。
- 「依頼テンプレート」は `templates\request-template.txt` に置く**中立な組み立て枠**で
  あり、ひな形とは役割が異なる。改修指示・出力指示の文面はテンプレートにも C# / JS にも
  持たない。AI の種類や渡し方に合わせて使用者が編集できる。
- どこが改修対象か・どう直すかの判断はチャット AI がやる。ツールは該当箇所を検出しない。
- チャット AI の返答をツールは解釈しない（パースしない）。人間が読んで、GUI で
  モジュールを選んで貼る。**選ぶ行為そのものが確認**になっている。
  間違えたら diff が真っ赤になって気づける。
- 結果としてツールは汎用化される。別のマニュアルを差せば別目的に使える。
  ツール側のコードは変わらない。

この思想から導かれる実装上の線引き（本書での用語）:

- **禁止（判断）**: 返答テキストからモジュール名・コードブロックを抽出する、
  変更内容を要約する、対象モジュールを推定する、といった「意味の解釈」。
- **許可（帳簿付け）**: 貼り付けテキストの改行正規化、コードフェンス行の除去、
  `Attribute VB_` 行の機械的な除去・再付与、貼った結果の diff 計算。
  これらは入力の意味を解釈せず、決まった規則を機械的に適用するだけの処理。
  （個別の規則は §8 に列挙。ここに無い正規化を実装時に増やさないこと）

### 1.3 UI 設計原則

既定のライトテーマは明るい紙面、ダークテーマは同じ机の夜間照明として設計する。
ダークはライトの反転ではなく、独立した意味トークン一式を持つ。

**進む道は常に 1 本**とし、右下の固定した［次へ］だけが前へ進める。装飾目的の
発光やガイドリングは使わない。青=作業中、緑=完了、灰=未処理、
赤=削除・失敗という状態辞書を、モジュール一覧、diff、ビルド結果、HTML レポートまで
統一する。詳細は §3.5。

## 2. 全体構成

### 2.1 技術構成

**PowerShell 5.1 + Add-Type(C#) + WPF + WebView2** のハイブリッド構成。

- `launch.vbs` で黒画面を一切出さずに起動。配布物の起動方法は launch.vbs
  ダブルクリックの一択（開発時のみ launch.bat でコンソール表示）。
- UI の実体は WebView2 内の HTML/CSS/JS。XAML（WPF）は殻。
- dotnet SDK 不要。フォルダをコピーするだけで動くこと。
- WebView2 DLL（SDK 1.0.3856.49）をリポジトリに同梱する。

### 2.2 外部依存を持たない

MacroStudio は単体で完結し、実行時に外部ライブラリを必要としない。

- VBA の抽出・書き戻し（OLE2 複合ドキュメントの読み書き、MS-OVBA 圧縮ストリームの
  展開・再圧縮）は **MacroStudio 自身の実装**として `src/` に持つ。
- diff アルゴリズムと VBA シンタックスハイライトも自前実装（`assets/js/`）。
- 実行時依存はリポジトリ同梱の WebView2 DLL と OS 標準コンポーネントのみ。

### 2.3 エンジンの実装位置

エンジン（OLE2 / VBA 圧縮 / 書き戻し）は、ホストと同じ Add-Type でコンパイルする
**C# クラスとして src/ 内に実装**する（子プロセスや別モジュールを作らない）。

理由:
- 中核はバイト列処理であり、C# で書くのが最も素直。
- 子 PowerShell プロセス + JSON ファイル受け渡しの複雑さ（起動待ち・文字コード・
  一時ファイル管理）が丸ごと消える。
- GUI から切り離した検証は、同じ src/*.cs を Add-Type するヘッドレスの
  テストスクリプト（tests/）で行える。

### 2.4 リポジトリ構成

```
macrostudio/
├── launch.vbs               # 本番起動（黒画面なし）
├── launch.bat               # 開発起動（コンソールあり）
├── macrostudio.ps1            # ホスト: src/*.cs を集約 → Add-Type → App.Run
├── src/                     # C#（ホスト + エンジン）。ASCII のみ、C# 5.0 構文
│   ├── 01_App.cs            # エントリ。AssemblyResolve、STA スレッド、WebView2 ランタイム確認
│   ├── 02_MainWindow.cs     # WPF 窓 + WebView2 + 仮想ホスト + D&D 受け
│   ├── 03_MessageRouter.cs  # JS⇔C# の id 付き request/response IPC
│   ├── 04_HostServices.cs   # ダイアログ、クリップボード読み書き、explorer /select、コード・差分ファイル出力、template / presets 読み、ログ
│   ├── 05_Ole2.cs           # OLE2(CFB) リーダ/ライタ（自前実装）
│   ├── 06_VbaCompression.cs # MS-OVBA 2.4.1 展開・圧縮（自前実装）
│   ├── 07_VbaProject.cs     # dir の MODULE レコードを正本とするモジュール一覧・コード取得・コードページ・書き戻し計画
│   └── 08_BookIO.cs         # xlsm/xlam/xlsb(zip) の入出力、コピー生成、ビルド、検証
├── assets/                  # UI 実体（日本語 OK）
│   ├── index.html
│   ├── fonts/ (Noto Sans JP / UDEV Gothic の TTF と OFL)
│   ├── css/  (variables / layout / flow / module-list / diff)
│   ├── js/   (screens / state / app / theme / host-bridge / diff /
│   │          diff-report / diff-view / vba-highlight /
│   │          preset-document / prompt-template)
│   └── messages/ (ホスト(C#)が表示する日本語文言 *.txt。src/ は ASCII のまま)
├── presets/                 # 依頼の正本（*.md、1 ファイル = 1 ボタン。§5.2.1）
├── templates/               # 依頼文（チャット貼付用）の中立な組み立て枠
├── lib/                     # WebView2 DLL 同梱（4 本）
├── docs/                    # SPEC.md（本書） / DEVELOPMENT.md
├── tests/                   # ヘッドレス検証スクリプト
└── README.md
```

`testdata/` は git 管理外とし、開発機ローカルで検証用ブックを置く
（[DEVELOPMENT.md](DEVELOPMENT.md) 参照）。

### 2.5 対応ファイル形式

判定は**拡張子ではなくファイルの中身**で行う。拡張子は入口のブロッカーにしない。

| 拡張子 | 中身 | 扱い |
|---|---|---|
| `.xlsm` | zip 内 `xl/vbaProject.bin`（OLE2） | 対応 |
| `.xlam` | 同上 | 対応 |
| `.xlsb` | 同上 | 対応。機構上は xlsm と同一経路（§15） |
| `.xls`  | ファイル全体が OLE2 | 読み取り対応。ビルドは検証（§9）を通った場合のみ成功 |
| その他 | — | zip なら vbaProject.bin を、OLE2 なら本体を VBA コンテナとして読む。どこにも VBA が無い場合だけ E-ATTACH-03 |

補足:
- VBA プロジェクトにパスワード保護が掛かったブック: 保護は VBE の閲覧ゲートであり
  モジュールストリーム自体は暗号化されない（MS-OVBA 仕様）ため、抽出・書き戻しとも
  影響を受けない**見込み**。実ファイルでの確認は未実施（§15）。

## 3. 画面構成

### 3.1 レイアウト

**1 画面 1 判断。** 使用者は常に 1 つのことだけを決め、右下の同じ位置にある
［次へ］で進む。全 10 画面を 4 つの手順（進捗）にまとめる。

```
┌────────────────────────────────────────────────────────────┐
│ MD MacroStudio │ ①ブックを読み込む ②AIへ依頼する ③返答を取り込む ④ブックを作る │ 最初から ◐ │ 48px
├────────────────────────────────────────────────────────────┤ 4px（進捗バー）
│ 手順 2 · 2/3  AIへ送る依頼文を用意しました       VBAリファクター │ 52px
├────────────────────────────────────────────────────────────┤
│                                                            │
│                   その画面の作業だけ                         │ 残り全部
│                                                            │
├────────────────────────────────────────────────────────────┤
│ ● この画面の次にすること              ［戻る］［次へ］        │ 68px
└────────────────────────────────────────────────────────────┘
```

- 上部: ブランド、4 手順の進捗、［最初から］とテーマ切替。進捗は現在地の表示専用で、
  クリックでは移動しない（移動は［戻る］［次へ］だけ）。
- 中央: その画面の作業。短い案内文（`.task-intro`）を通常の文章として置き、
  ラベル付きの色面やアイコン付きコールアウトは使わない。
- 下部: 固定操作領域。左に次にすることの 1 行、右に **［戻る］［次へ］を常に同じ位置・
  同じ寸法で両方表示**する。最初の画面では戻るが無効、最後の画面では次へが無効。
  必要な選択や入力が揃うまで次へは灰色で、揃った瞬間に青へ変わる（約 200ms）。
- 画面固有の操作（ファイル選択、コピー、取り込み、手動修正、フォルダを開く）は
  中央に置き、固定の戻る／次へと入れ替えない。

### 3.2 寸法と 1366x768 対応

想定最小解像度 1366x768（作業領域 高さ約 728px、100% スケール）。

| 領域 | 高さ |
|---|---|
| トップバー | 48px 固定 |
| 進捗バー（細線） | 4px 固定 |
| 画面見出し | 52px 固定 |
| 中央（作業領域） | 残り全部 |
| 固定操作領域 | 68px 固定 |

コード表示（diff）と依頼文の編集欄以外では、**アプリ全体をスクロールさせない**。
一覧やコードなど中身が伸びる領域は、その領域の内側でスクロールする。
ボタンは標準 40px、ツールバーやカード内の補助操作は 34px の 2 種類に揃える。
完了画面だけ巨大なボタンにはしない。

### 3.3 モジュールの一覧（確認画面の左ペイン）

モジュール一覧は確認画面（画面 6）の「変更内容を見る」を開いたときにだけ左に置き、
そこでのモジュールツリーとして働く。取り込み画面（画面 5）には置かない。

- 載せるのは**返答に入っていたモジュールだけ**。触れていないモジュールは並べない。
- 表示順は VBE のプロジェクトツリーと同じ: ドキュメント → フォーム → 標準 → クラス、
  同種内は名前順。
- 標準モジュール / クラスモジュール / フォームモジュール / シートモジュールの
  見出しで区分し、その中を名前順に並べる。
- 1 行 = 状態ドット + モジュール名 + 状態語（+N 行 / 変更なし）。
- クリックで選択。選択した行が右側の diff になる。ここでの選択は表示だけを変え、
  何を書き戻すかは変えない（採否はパッケージ単位。§10.2）。

### 3.4 確認画面のメイン領域（インライン diff）

diff は **GitHub と同じインライン（unified）形式**とする。左のモジュールツリーで
選んだモジュールの差分が、右側いっぱいに縦一列で並ぶ。

- 1 行 = `改修前の行番号` / `改修後の行番号` / `マーカー（- +）` / `コード` の 4 列。
  削除行は赤、追加行は緑、変更のない行は無色で、行全体に色を付ける。
- 変更行は「削除行 → 追加行」の 2 行に開く。行内差分のマークは両方に残す。
- 取り込み画面（手順3・1/3）では、左に現在のモジュール、右に取り込み手順と
  ［クリップボードから取り込む］を置く。取り込むとインライン diff の画面へ進める。
- diff 表示中は直接編集できない。編集は**手動修正**画面だけで行う。
- **手動修正**: diff ツールバーの［手動修正］で、左＝現在のコード、
  右＝貼り付け内容の編集欄（textarea）に切り替わる。誤って付いたコード
  フェンスや軽微な写し間違いをその場で直し、［修正を反映］で §8 と同じ
  正規化を通して取り込み直す（diff・変更行数・状態は再計算）。
  ［編集をやめる］で編集を破棄して diff に戻る。編集欄・入力欄への
  Ctrl+V は通常の貼り付けとして扱い、全体貼り付けには奪わせない。
  未反映の編集が残る画面移動・モジュール切替・新規取り込み開始・
  別ブック添付では、黙って破棄せず確認ダイアログを出す。
- **採否のボタンは置かない**: 取り込めた内容がそのまま書き戻しの対象になる。
  やめたいときは［戻る］で取り込み画面へ戻る（§5.3）。
- 新規標準モジュールは名前を手入力してから同じクリップボード経路で取り込む。
  貼り付け内容から名前や種別を抽出・推測しない。取り消すと新規項目自体を一覧から除く。
- equal / added / removed の全行に VBA シンタックスハイライトを適用する。
- 変更行では共通接頭辞・接尾辞を除いた行内差分をマークし、マーク内の空白を `·`、
  タブを `→` で可視化する。
- 新規モジュールは元コードが無いため全行が追加行になる。その旨の帯を表の上に出す。
- 長い行は切り詰めず横スクロールで表示し、任意で「折り返し」を有効にできる。
- 「変更箇所のみ」は常設し、200 行超のモジュールだけ既定 ON とする。省略帯は
  `…n 行を表示` のボタンで展開できる。
- 連続する非 equal 行を変更ブロックとし、前後ボタンまたは Alt+↑ / Alt+↓ で移動する。

diff 描画は自前実装（Monaco 不使用）。§13.1 参照。

### 3.5 進行の示し方

進行を示すのは次の 3 つだけで、装飾目的の発光やガイドリングは使わない。

| 合図 | 意味 |
|---|---|
| 進捗バーの現在地と細い塗り | いま 4 手順のどこにいるか |
| ［次へ］の灰 → 青 | この画面で必要なものが揃った |
| 選択の SVG チェック、コピー完了の表示 | いま押した操作の結果 |

選択カードは押しただけでは遷移せず、チェックが付いて［次へ］が有効になる。
画面遷移は約 200ms のフェードと進行方向への小さな横移動だけを行い、
常時動く装飾は置かない。

### 3.6 テーマ、トークン、フォント

- `assets/css/variables.css` を色、字、間隔、角丸、影、寸法の正本とする。他の CSS に
  1px 罫線以外の px 値、色の直値、テーマ分岐を書かない。
- ライトを既定とし、ダークはトップバー右端のボタンで明示的に切り替える。
  選択は `localStorage` の `macrostudio.theme` に保存し、初回描画前に復元する。
- ライトとダークは独立した意味トークン一式を持つ。指定色は
  `tests\test-design-system.ps1` で双方 45 色ずつ完全一致を検査する。
- UI は同梱の Noto Sans JP 可変 TTF、コードと diff は同梱の UDEV Gothic
  Regular / Bold TTF を使う。ライセンスは各 TTF と同じフォルダへ同梱する。
- diff HTML レポートは共有・印刷用の書類として、常にライトの指定色で自己完結生成する。

## 4. ワークフロー（用途で 2 つに分かれる 12 画面）

| # | 画面 | この画面で決めること | ［次へ］が有効になる条件 |
|---|---|---|---|
| 0 | Excelブックを読み込みます | 対象ブック | ブックを読み込めた |
| 1 | 読み込んだマクロを確認します | 読み取り結果の確認 | ブックを読み込み済み |
| 2 | このマクロをどうしたいか選びます | 改修 / 診断 | どちらかを選んだ |
| 3 | どんな◯◯をするか選びます | 依頼の内容（プリセット 1 つ） | 1 つ選んだ |
| 4 | いくつか教えてください | 質問への回答（`## 質問` のあるひな形のみ） | 1 問以上答えた |
| 5 | AIへ送る依頼文を用意しました | 依頼文の内容（必要なら編集） | 依頼文が空でない |
| 6 | AIチャットへ◯◯を依頼します | チャットへの受け渡し | 依頼文をコピーし、フォルダも開いた |
| 7 | AIの返答をまとめて取り込みます | 返答の一括取り込み | 1 個以上のモジュールを取り込めた |
| 8 | 取り込んだ変更を確認します | 内容の確認（採否の再確認はしない） | 変更が 1 件以上あり、手動修正を開いていない |
| 9 | 作成する改修済みブックを確認します | 出力ファイル名 | 名前が正しい（元の拡張子・区切り文字なし） |
| 10 | 改修済みブックをビルドしています | （自動） | — |
| 11 | 改修済みブックを作成しました | 出力フォルダを開く / 完了 | （［次へ］の位置は［完了］になる） |

- 分岐は 1 か所だけ。3 → 選んだひな形が `## 質問` を持てば 4 へ、無ければ 5 へ。
- **診断は 6 が終点**。6 は依頼文をコピーしてファイルを渡す画面であり、
  渡し終えればその依頼は完了する。よって 6 の［次へ］の位置には［完了］が出る
  （コピーとフォルダを開くの両方が済むまで無効。条件は［次へ］と同じ）。
  診断のためだけの画面やビルダーは持たない。7 以降は改修だけが通る。
- 進捗バーは用途で変わる。改修は 4 手順、診断は 2 手順（読み込む / AIへ渡す）。
- 2 と 3 は選んでも自動で進まない。選択は［次へ］で確定する。
- 4 は 1 問ずつ表示する。上の丸（ビーズ）で位置と回答済みが分かり、
  左右の矢印か丸のクリックで移動する。問数が多いときは中間の丸を畳む。
  質問間の移動と、画面間の［戻る］［次へ］は別の操作として区別する。
- 5 の依頼文には、4 で答えた内容が【質問への回答】として折り込まれる。
  質問はひな形の性質であって用途の性質ではない。改修側のひな形が `## 質問` を
  持てば、同じ画面が同じように出る。
- 5 で依頼文を作った時点で、今回の依頼 ID（UUID v4）が発行される。
- 5 は 1 回の操作で返答全体を取り込む。モジュールツリーも個別の貼り付け欄も置かない。
- **取り込めた時点で、それが書き戻す対象になる**。6 に採用ボタンは置かない。
  やめたいときは［戻る］で 5 へ戻り、取り込み直すか別の返答を渡す。
- 11 の［次へ］の位置にも［完了］を置く。押すと最初の画面へ戻り、次のブックへ移れる。
- 6 では「マクロが読み書きするExcelシートも一緒に添付する」ことを 1 行で案内する。
- ［戻る］は実際に通った経路を逆にたどる。ビルド中（8）だけは戻れない。

### 4.1 段階的開示（Progressive disclosure）

各画面は「いま何をするか」「必要な入力」「主要ボタン」「対処が必要な警告」だけを
常時表示し、それ以外は 1 段だけ開閉できる領域へ入れる。

| 画面 | 常時表示 | 開いて見るもの（ラベル） |
|---|---|---|
| 1 | 読み取り件数の見出し | モジュール名と行数（「読み取った内容を見る」） |
| 5 | 依頼文が用意できた見出し | 依頼文の全文と編集欄（「依頼文を確認・編集」） |
| 6 | 受け渡しの 2 枚のカードと添付の案内 | 実行フォルダと作成ファイル（「作成されるファイルの場所を見る」） |
| 7 | 取り込み結果の見出し | AI が書いた改修内容の要約（「AIが書いた改修内容を見る」） |
| 8 | 取り込み結果の要約 | モジュール一覧とインライン Diff（「変更内容を見る」） |
| 9 | 出力ファイル名の入力欄 | 実行フォルダと作成ファイル（「作成されるファイルの場所を見る」） |

- 常時出すのは「この画面ですること」「必要な入力・選択」「主要ボタン」「対処が必要な
  警告」だけ。パスや作成予定ファイルのような参考情報は既定で畳む。
- 開閉のラベルは、開くと何が出るかを述べる。「詳細設定」のような名前は使わない。
- 開発の経緯が透ける説明（「元のブックはまだ 1 文字も変わっていません」など、
  初めて使う人が知る必要のない安心材料）は書かない。
- 入れ子は 1 段まで。開閉領域の中へさらに開閉領域を置かない。
- 警告と、操作がまだできない理由は、開閉領域へ入れない。
- 閉じている領域の中身は `visibility: hidden` でタブ順から外す。
- 開閉は約 200ms の高さアニメーションで、画面が飛ばないようにする。
- Diff のコード表示だけは内部スクロールしてよい。アプリ全体は
  1366x768 でスクロールせず、フッターは固定のままにする。

## 5. 画面別詳細仕様

### 5.1 ブックの読み込み（画面 0・1）

画面 0: 大きなドロップゾーン（クリックでファイル選択も兼ねる）。

処理フロー:

1. D&D またはファイル選択でパスを受け取る（D&D の実装方式は §7.4）。
2. 入口では拡張子も排他ロックも検査しない。Excel で開いたままのブックも添付できる
   （読み込みは共有読み取りで、元ファイルは変更しない）。
3. エンジンでブックを読み込む（コピーをメモリに読むだけ。元ファイルはロックしない。
   読み込み後にファイルハンドルを保持しない）。読取は多経路で再試行する（§5.1.1）。
   ある経路が失敗しても別経路で読み直し、読めたモジュールとソースは必ず保持する。
4. 成功: 画面 0 に留まり、選んだブックのカードと［選び直す］を表示して［次へ］を
   有効にする。部分的な不整合があった場合は成功させたうえで警告を一度だけ表示し、
   その後の操作を禁止しない。
5. 失敗: §12 のエラー分岐。どの経路でも VBA が見つからない場合だけ E-ATTACH-03。

画面 1: ブック名・パス・モジュール数・合計行数・読み取り警告と、モジュール名の一覧。
［別のブックを選ぶ］で画面 0 へ戻る。

別ブックの添付し直しはいつでも可能。ただし取り込み済みの変更が 1 件でもあれば
確認ダイアログを出し、［破棄して進む］でのみ全状態をリセットする。

#### 5.1.1 VBA 読取の経路

上から順に試し、**モジュールが 1 つでも読めた時点で採用**する。後段へ落ちた場合は
警告（`warning:true`）を 1 度だけ出し、操作は継続する。

| # | 経路 | 使う場面 |
|---|---|---|
| 1 | ZipArchive で `vbaProject.bin`（名前一致 → 大小無視 → `.bin` かつ VBA ストレージを持つもの） | 正常な xlsm / xlam / xlsb |
| 2 | ZIP central directory を自前で走査して local header から取り出す | EOCD やアーカイブ構造が壊れている |
| 3 | ファイル全体から local file header を走査（stored / deflate 双方） | central directory が失われている |
| 4 | ファイル先頭が OLE2 署名ならファイル自体をコンテナとみなす | xls など |
| 5 | ファイル中の任意位置の OLE2 署名から VBA コンテナを探す | 非圧縮格納されたメンバなど |
| 6 | 生バイトから MS-OVBA 圧縮コンテナを走査し、`Attribute VB_Name` を持つものをモジュールとして復元 | CFB directory ごと壊れている |

モジュール単位でも同様に多経路で読む。dir の MODULEOFFSET を使い、そこに
`Attribute VB_Name` が無ければストリームを後方から再走査する。1 つのモジュールの
失敗が他のモジュールを巻き込まないよう、モジュール単位で例外を閉じる。
dir が壊れていれば PROJECT ストリームの列挙を、PROJECT も壊れていれば VBA ストレージ
配下のストリームを直接読む。

新規モジュール追加は dir / PROJECT / PROJECTwm を書き換えるため、**3 者が厳密に読めて
互いに一致している場合だけ**有効にする（`ProjectModulesOffset` を保持する条件）。
書き込み時の文字コード変換は常に厳密（表現できない文字はビルド失敗にし、
置換文字をブックへ書かない）。

### 5.2 依頼を作る（画面 2〜4）

**画面 2**: `presets/*.md` から作る「改修の目的」の一覧。1 ファイル 1 枚のカードで、
H1 を目的名、改修指示の 1 行目を要約として出す（§5.2.1）。押すとチェックが付き、
その Markdown の改修指示が依頼文に、出力指示が現在の出力指示になり、
**この依頼の ID（UUID v4）が発行される**（§6.5）。押しただけでは進まない。
書式が不正なファイルはカードにせず、一覧の下に理由付きで並べる（§5.2.2）。

一覧は画面 2 に入るたび `getAppInfo` で読み直す。ファイルの追加・削除・
リネーム・H1 の変更は、アプリを再起動しなくても反映される。

**画面 3**: 用意できた依頼文の見出しと、「依頼文を確認・編集」の開閉領域。
開くと依頼文の全文が編集できる（自由編集はこの画面だけ）。文字数と、
いま付いている出力指示の由来（ひな形名）を添える。

**画面 4**: ［次へ］を押した時点で**この改修専用の実行フォルダ**（§5.4）を作り、
`request.md` と `source-code.md` を書き出してからこの画面へ進む。画面には
「依頼文をチャットへ貼り付ける」「コード全文ファイルを添付する」の 2 枚のカードと、
実行フォルダのパス・作成済みファイル名を出す。
［依頼文をコピー］と［ファイルの場所を開く］の**両方**が済むまで［次へ］は無効。
押した後のボタンは「コピーしました」「フォルダを開きました」に変わる。

#### 5.2.1 ひな形ファイルの書式

1 ファイル = 1 つの依頼の正本。名前・改修指示・出力指示をすべてその 1 枚に持ち、
使用者はファイルを差し替えるだけで 3 つとも変えられる。共通化のための外部ファイルや
コード定数は作らない（複数ファイルで出力指示が重複するのは許容する）。

```markdown
# VBAリファクター（動きを変えずに整理・改善する）

<!-- 編集者向けのメモ。チャットへ渡す依頼文には入らない -->

## 改修指示

（このひな形の目的。依頼文入力欄へ入る）

## 出力指示

（返答のしかた。1 つのコードブロック、§6.5 の区切り行、最小限の変更、
　無関係な行・順序・空白・コメント・宣言・名称の維持、変更モジュールと
　新規モジュールの全文、チャット本文で返すこと）
```

任意の見出しが 2 つある。

- `## 用途` … `改修` か `診断`。省略時は `改修`。
  用途は画面 2 の選択と対応し、選んだ用途のプリセットだけが画面 3 に並ぶ。
- `## 質問` … アプリが画面 4 で聞く項目。`- 質問文` で 1 問、その下へ字下げして
  `- 選択肢` を並べると選択式になる。字下げが無ければ自由記述（複数行）。
  この見出しがあるプリセットだけが、質問の画面を通る。

解釈規則（`assets/js/preset-document.js` が唯一の実装。C# 側は同じ規則を持たない）:

1. `<!-- ... -->` を先に全除去する。複数行・行内どちらも可。閉じられていなければ不正。
2. 残りの最初の H1 をプリセット名とする。コードフェンス内の `#` は見出しとみなさない。
3. `## 改修指示` と `## 出力指示` の 2 見出しで本文を分ける。見出し名は固定。
   `###` 以下は本文の一部として残す。
4. 各節の前後の空行を落とし、改行は CRLF に正規化する。
5. 名前と 2 節が揃って初めて有効なひな形とする。H1 やコメントは依頼文へ渡さない。
6. `{{REQUEST_ID}}` は、目的を選んだ時点で発行した依頼 ID へ置換してから
   チャットへ渡す。プレースホルダのまま外へ出ることはない。

同梱するひな形（差し替え自由。コードはファイル名も表示名も参照しない）:

| ファイル | 用途 | 目的 |
|---|---|---|
| `01_VBAリファクター.md` | 改修 | 動きを変えずに整理・改善する（一般リファクタ） |
| `02_Win32API依存をなくす.md` | 改修 | Win32 API を使わない形へ直す |
| `03_自分で書く.md` | 改修 | 改修内容を自分で書く |
| `04_診断する（改修はしない）.md` | 診断 | 新しい端末で動くかを見てもらう |
| `05_相談する（進め方を決める）.md` | 診断 | 質問に答え、AI と改修方針を決める |
| `06_自分で聞く（診断）.md` | 診断 | 聞きたいことを自分で書く |

`04` は新しい業務端末の制約（Win32 API・外部プロセス起動が使えない、ブックが
SharePoint / OneDrive 上に載って `ThisWorkbook.Path` が URL になる、端末依存の
固定値、古い部品）を観点として並べ、**コードを書かせずに**問題箇所と直し方の方針を
報告させる。`05` は `## 質問` を持ち、回答を折り込んだ 1 通目で AI と壁打ちし、
最後に改修方針をまとめさせる。どちらも返答をアプリへ取り込まないので、
区切り行や `{{REQUEST_ID}}` を持たない。

`01` の改修指示は、置換規則の一覧ではなく**判断基準**として書く。配列一括読み書き、
`Select` / `Activate` の排除、`Value2`、`Dictionary`、`ReDim Preserve`、
Application 設定の停止範囲などを「元コードとデータ量を見て選ぶ」形で述べ、
意味を確かめない一括置換・過剰な細分化・推測による複雑化を明示的に禁じる。
観測できる動作（公開入口・呼び出し順・出力・書式・メッセージ）は変えない。

#### 5.2.2 書式が不正なファイルの扱い

黙って旧来の動作へ読み替えることはしない。次はすべて**不正**とし、選べなくする。

| 事象 | 例 |
|---|---|
| H1 が無い / 2 つ以上 / 名前が空 | 旧形式の本文だけのファイル |
| `## 改修指示` または `## 出力指示` が無い / 重複 | 片方だけのファイル |
| 節の本文が空 | 見出しだけのファイル |
| 見出しの外に本文がある | H1 の前後に書いた前置き |
| 知らない `##` 見出し | `## メモ` など |
| コメントが閉じられていない | `-->` の書き忘れ |

不正なファイルは画面 2 の「読み込めないひな形」欄にファイル名と理由を並べて表示し、
押せない状態にする。押下時に読み直して不正になっていた場合は E-PRESET-01 とし、
依頼文と出力指示を変更しないまま一覧を読み直す。ホストが UTF-8 として読めない
ファイルも同じ欄に「読み取れませんでした」として残す（一覧から消さない）。

### 5.3 返答を取り込む（画面 5・6）

前提: ブックを読み込み済みで、この依頼の ID があること。返答は 1 つの
コードブロックにまとまっている（§6.5）。

**画面 5（取り込み）**: 置くのは［クリップボードからAIの返答を取り込む］の
1 ボタンだけ。モジュールツリーもモジュール選択も個別の貼り付け欄も置かない。
Ctrl+V も同じ動作をする。

1. クリップボードのテキストを取得（C# 側 `Clipboard.GetText()`。§7.3）。
2. §6.5 の規則で解析する。コードフェンス（``` 行）は有っても無くてもよい。
3. 依頼 ID の一致、区切りの対応、終端行、モジュールの重複、種類と名前、
   個数の整合を検査する。1 つでも通らなければ**何も取り込まない**。
4. 通ったら、返答に入っていたモジュールを**まとめて**取り込む。各モジュールへ
   §8 の正規化を適用し、現在のコードと同一なら「変更なし」として扱う。
5. 成功時は「3個のモジュールを取り込みました。」の見出しと、既存・新規の内訳を出す。
   返答に SUMMARY（§6.5）が入っていれば「AIが書いた改修内容を見る」で読める。
   失敗時は例外や記号を出さず、次にどうするかだけを 1 文で伝える（E-INTAKE-01）。

既存モジュールの種類は**ブック側を正本**とする。返答の `<種類>` が食い違う場合は
ブックの種類のまま取り込み、画面 6 の見出し直下に「どのモジュールの種類を
読み替えたか」を常時表示の警告として出す（開閉領域へは入れない）。
新しく増やすモジュールは標準モジュールだけを受け付ける（§13.3）。それ以外は
取り込みを断る。

**画面 6（確認）**: 見出しは「3個のモジュールへ変更を取り込みました」のような要約。
「変更内容を見る」を開くと、左のモジュール一覧と、選んだモジュールの
インライン Diff（§3.4）が出る。手動修正もこの中で行う。

- **取り込めた時点で、それが書き戻す対象**。採用ボタンも確認ダイアログも置かない。
  「見る → 進む」で 1 画面 1 判断を保ち、同じ判断を二度させない。
- やめたいときは［戻る］で画面 5 へ戻る。取り込み直すか、別の返答を渡せばよい。
  元ブックには何も起きない。
- 手動修正を開いている間は［次へ］を止める。反映するかやめると再び進める。
- 「違う」となったら［戻る］で依頼の画面まで戻り、言い直せる。往復しても
  取り込み済みの状態は保持する。ブックを替えたときだけ全リセット。

補足: ひな形の指示（変更したモジュールのみ出力）にもかかわらずチャット AI が
無関係なモジュールを余計に返してきた場合、そのモジュールも取り込みの対象になるが、
画面 6 の Diff で確認でき、そのまま進めなければブックには反映されない。
返答の内容をツールが推測して除外することはしない。

### 5.4 ブックを作る（画面 9〜11）と出力フォルダ

**出力フォルダ契約**: 元ブックのフォルダ直下に `MacroStudio` フォルダを作り、
実行ごとに次のフォルダを作る。

```
<元ブックのフォルダ>\MacroStudio\<ブック名（拡張子抜き）>_<yyyyMMdd_HHmmss>\
    request.md                      … チャットへ貼り付けた依頼文
    source-code.md                  … 添付したコード全文（§6.2 の固定形式）
    <出力ファイル名>                  … 改修済みブック（既定 <ブック名>_macrostudio<元の拡張子>）
    diff-report.html                … 改修前後の差分レポート（全モジュール）
    result.md                       … 改修の概要メモ（何をどう直したか）
```

診断のときは `request.md` と `source-code.md` の 2 つだけを作る。

- 実行フォルダは**依頼作成時点（画面 3 →4）で確定**し、その実行の後続の出力も
  同じ場所へ置く。新しい依頼を作ると新しいフォルダになる。
- 元ブックは親フォルダでそのまま残す（**上書きしない**）。
- ［ファイルの場所を開く］［出力フォルダをエクスプローラーで開く］はこの実行フォルダを開く。
  パスのコピーボタンはどの画面にも置かない。

画面フロー:

1. **画面 7**: 書き戻し・変更なし・新規追加・元ブック保持の集計と、出力ファイル名の
   入力欄、実行フォルダと作成予定ファイルの一覧を表示。名前はファイル名だけを許し、
   区切り文字・`..`・元と違う拡張子は受け付けない（ホスト側でも同じ検査をする）。
2. **画面 8**: ［次へ］でビルドを開始し、進行中を表示する（通常 1〜2 秒想定）。
   この画面では戻る・次へとも無効。
3. **画面 9（成功）**: 実行フォルダのパス、標準サイズの
   ［出力フォルダをエクスプローラーで開く］、作成した 4 ファイルの一覧。
   固定操作領域の［次へ］の位置には［完了］を置き、押すと最初の画面へ戻す。
   「Excel で開いてマクロの動作を確認してください」の案内は 1 行の文章で置く。
4. **画面 9（失敗）**: モジュール別の結果表（§9.4）と［もう一度ビルドする］。
   出力ファイルは残さない。元ファイルは無傷。

ビルドは**元ファイルを上書きせず別名保存**。差分 HTML はインライン CSS のみを持つ
自己完結ファイルとし、差分計算は画面と同じ `assets/js/diff.js` を使う。
差分 HTML には**変更しなかったモジュールも含める**（種別ごとのツリーに並び、
本文は全行が文脈行、見出しは「変更なし」）。改修後のブックの記録として、
1 ファイルで全モジュールを読めることを優先する。
HTML の生成・書き込みだけが失敗した場合はログとエラートーストに通知するが、
完成済みブックの成功は取り消さない。
ビルド後も［戻る］で取り込みや依頼へ戻って続きの改修 → 再ビルドができる。

## 6. 依頼の受け渡し形式（コードファイルとプロンプト）

### 6.1 二つの成果物

② は次の二つを作る。判断材料（コード）と依頼（指示）を分けるのは、添付
ファイル内で指示文・散文とコードが混在すると、チャット AI がコードを
「全文を取得できない」と誤認する実測に基づく。

- **コード全文ファイル**（添付用・`source-code.md`）: 取得した VBA コードだけを
  含むプレーンテキスト。§6.2 の固定形式で、依頼文・操作説明・注記の散文を一切
  含めない。使用者はこのファイルをチャット AI に添付する。
- **依頼プロンプト**（チャット貼付用）: `templates\request-template.txt` の枠に、
  選んだひな形の改修指示（＋使用者の書き足し）と出力指示を差し込んで生成する
  テキスト。同じ内容を実行フォルダへ `request.md` としても書き出す。画面 5 の
  ［依頼文をコピー］でクリップボードへ入り、使用者がチャット本文へ貼り付ける。
  コード本文はクリップボードへ入れない。

設計上の確定事項:

- コードファイルは**常に全モジュール**を含める。載せるモジュールを絞り込む・
  選択する UI は作らない（使用者に「どれを載せるか」を判断させない）。
- ファイル添付方式のため、サイズ上限を理由としたプロンプト分割・バッチ送信の
  設計は入れない。
- 依頼作成の出口は「実行フォルダの作成 + request.md / source-code.md の書き出し」に
  絞り、コピーとフォルダを開く操作は画面 5 の中央に置く（§5.4）。コード本文の
  受け渡し経路は添付ファイルだけとする（§14 とも整合）。

### 6.2 コード全文ファイル（固定形式）

コードファイルの形式はツール側で固定し、テンプレートでは変更できない
（チャット AI が正常に読める形式を、互換性の契約として保護するため）。
出力は UTF-8 BOM 付き、改行は CRLF、末尾は CRLF 1 個とする。

構成（見出し等の固定文字列はすべて ASCII）:

1. 80 桁の `=` 罫線で挟んだヘッダ: ` <ブック名> - VBA Source Code` と
   ` Generated: <yyyy-MM-dd HH:mm:ss>`。
2. `MODULE INDEX` と 40 桁の `-` 罫線。種別ごと
   （Standard Modules / Class Modules / UserForms / Document Modules）に
   `    <名前>.<拡張子> (<行数> lines)` を列挙し、
   `  Total: <合計行数> lines across <モジュール数> modules` で締める。
3. モジュールごとに、80 桁の `=` 罫線で挟んだ ` <名前>.<拡張子>` 見出しと、
   Attribute ヘッダ除去済みのコード全文（§6.4）。空のモジュールは見出しだけを
   出し、本文や注記は書かない（空であることはプロンプト側の一覧で伝える）。

### 6.3 依頼プロンプトと差し込み変数

［依頼を準備する］を押すたびに `templates\request-template.txt` を strict UTF-8
で読み直す。起動後に編集した内容も次回生成へ反映する。ファイルが無い、読み取れない、
UTF-8 として不正、または変数が不正な場合は E-GEN-02 で中止し、内蔵文面などへ
fallback しない。

| 変数 | 必須 | 差し込む値 |
|---|---|---|
| `{{REQUEST_TEXT}}` | 必須 | 依頼文入力欄の内容（ひな形の改修指示 + 使用者の書き足し） |
| `{{OUTPUT_RULES}}` | 任意 | 選んだひな形の出力指示。`【出力指示】` + 改行 + 本文の形に整えて差し込む。ひな形未選択なら空文字（見出しごと出ない） |
| `{{BOOK_NAME}}` | 任意 | 対象ブックのファイル名（ディレクトリを含まない） |
| `{{MODULE_COUNT}}` | 任意 | モジュール数 |
| `{{TOTAL_LINE_COUNT}}` | 任意 | 全モジュールの合計行数 |
| `{{MODULE_LIST}}` | 任意 | `- 名前（種別, 行数）` 形式に整形した全モジュール一覧 |
| `{{CODE_FILE_NAME}}` | 任意 | 添付するコード全文ファイル名（`source-code.md`） |
| `{{REQUEST_ID}}` | 任意 | 今回の依頼 ID（UUID v4。§6.5）。ひな形の出力指示側で使うのが主で、枠から使うこともできる |

`{{REQUEST_TEXT}}` は 1 回以上必要。任意変数は省略でき、既知変数は複数回使える。
未知の `{{NAME}}` または壊れた変数表記は E-GEN-02 とする。旧形式の
`{{MODULE_SOURCE_BLOCKS}}` は廃止済みで、テンプレートに残っている場合も
E-GEN-02 で明示的に停止する（コードはコードファイル側に出力される）。
値は文字列として改行だけを CRLF へ正規化して差し込み、内容の解釈・エスケープ・
代替値への置換は行わない。差し込んだ値の中にある `{{NAME}}` 形式の文字列も
変数として再解釈しない。変数値末尾とテンプレート側直後の改行は重複分を
重ね合わせ、値が末尾改行を持つ場合もテンプレートで定めた段落境界を保つ。

モジュール種別の表記: 標準モジュール / クラスモジュール / フォームモジュール /
ドキュメントモジュール。

同梱する `templates\request-template.txt` が枠の単一定義である。C# または JS に
同じ枠を fallback として持たない。テンプレートが AI へ直接述べるのは、対象の
前提だけに限る:

- 添付ファイルが対象ブックの VBA コード全文であり、省略がないこと。ソースが
  欠落している・省略されていると判断せず、追加の資料を求めないこと。
- 0 行のモジュールは元から空であること（対象モジュール一覧の注記）。

**返答のしかた（出力指示）はテンプレートに書かない。** 最小限の変更、無関係な行・
順序・空白・コメント・宣言・名称の維持、変更モジュールと新規モジュールの全文、
チャット本文のコードブロックで返すこと（ダウンロード用ファイルで返さないこと）、
返答の区切り形式（§6.5）や Attribute 行の扱いといった指示は、選んだひな形の「## 出力指示」が
持つ（§5.2.1）。ひな形を選ばずに手書きした依頼では出力指示は付かない。
ツールが代わりの文面を補うことはしない。

使用者はこのファイルを直接編集して、枠の構成を変更できる。画面 3 は実内容の
固定プレビューを持たず、編集した依頼文そのものを見せる。既定ファイルと同梱ひな形を使った
生成結果は、プロンプトとコードファイルの双方を回帰テストで byte 単位に固定する。

補足:
- 同梱ひな形の出力指示は §6.5 の 1 コードブロック形式を返答側に指定する。
  ひな形本文の `{{REQUEST_ID}}` は、依頼文を組み立てる前に今回の依頼 ID へ
  置換する。プレースホルダのままチャットへ出ることはない。
- 使用者がチャットで行う操作（依頼文の貼り付けとファイル添付）は画面 4 で案内する。
  ツールはチャット AI 側の操作には関与しない。

### 6.4 Attribute 行の扱い

- 抽出時: 各モジュール**先頭の連続した** `Attribute VB_*` 行群（ヘッダブロック）を
  分離して保持し、画面表示・コードファイルには**含めない**（VBE でも見えない行であり、
  使用者とチャット AI の双方にノイズのため）。コード途中のプロシージャ属性
  （`Attribute xxx.VB_UserMemId` 等。稀）はコードの一部としてそのまま残す。
- 同梱ひな形の出力指示でチャット AI にも「先頭に Attribute 行を付けない」よう指示（§5.2.1）。
- 貼り付け時: 万一先頭に含まれていても機械的に除去（§8。先頭ブロックのみ。
  抽出時と同じ規則にすることで、コード途中の属性を巻き添えにしない）。
- ビルド時: 保持しておいた**元のヘッダをそのまま先頭に再付与**して書き戻す。
  `Attribute VB_PredeclaredId` 等の意味を持つ属性が失われることを防ぐ。
- 新規標準モジュールだけは、C# 側で `Attribute VB_Name` を生成する。
- 帰結として既存モジュールの Attribute 行は変更できない（用途上不要。§14）。

### 6.5 返答パッケージ形式（1 コードブロック・依頼 ID 付き）

AI の返答は、変更したモジュールと新しく作ったモジュールの全文を**ちょうど 1 つの
コードブロック**にまとめたものとする。取り込みは 1 回の操作で全体を読む（§5.3）。

**依頼 ID（request nonce）**: 目的を選んだ時点でアプリが UUID v4 を 1 つ発行する。
乱数であり、コードや依頼文から計算されるハッシュではない。AI にハッシュや
チェックサムを計算させることはしない（ひな形にもそう書かない）。
ID は依頼プロンプトの区切り行の中に埋め込まれ、返答はそれをそのまま書き写す。

**区切り行**: 行全体が区切りである場合だけ区切りとして扱う（前後の空白は無視）。

```
'@MACROSTUDIO <依頼ID> SUMMARY BEGIN
（何をどう直したかの要約。マクロを書かない人にも分かる言葉で）
'@MACROSTUDIO <依頼ID> SUMMARY END
'@MACROSTUDIO <依頼ID> BEGIN <種類> <モジュール名>
（そのモジュールの全文）
'@MACROSTUDIO <依頼ID> END <種類> <モジュール名>
'@MACROSTUDIO <依頼ID> COMPLETE <モジュールの数>
```

- 先頭が `'` なので、区切り行はそのまま VBA のコメントとして正しい。
- `<種類>` は `standard` / `class` / `form` / `document`。
- モジュールの中に `'@MACROSTUDIO ...` に似た文字列があっても、行全体が
  この依頼 ID を持つ区切りでない限りモジュールは終わらない。曖昧な文字列分割は
  しない。
- コードフェンス（``` 行）は有っても無くてもよい。モジュールの外側にある行は
  読み飛ばし、モジュールの中の行はそのまま取り込む。
- SUMMARY の中身は散文であり、コードとして扱わない。取り込み画面の
  「AIが書いた改修内容を見る」で表示するだけで、ブックへは書き戻さない。
  要約をコードブロックの外へ書かせないのは、使用者がコピーするのが
  コードブロックだけだからである。SUMMARY が無い返答も取り込みは成功し、
  その場合は要約の開閉が出ないだけになる。

**検証**（`assets/js/response-package.js` が唯一の実装。1 つでも通らなければ
何も取り込まない）:

| 検査 | 断る理由 |
|---|---|
| 依頼 ID がこの依頼のものか | 別の依頼への返答 |
| 区切りが 1 つでもあるか | 取り込める形が無い |
| BEGIN と END が 1 対 1 で対応するか | 区切りが揃っていない |
| BEGIN の入れ子が無いか | 区切りが揃っていない |
| `COMPLETE` があるか | 返答が途中で切れている |
| `COMPLETE` の数とモジュール数が一致するか | 区切りが揃っていない |
| 同じモジュールが 2 回無いか | 重複 |
| `<種類>` が既知か | 知らない種類 |
| モジュール名が VBA 識別子として妥当か | 使えない名前 |
| 各モジュールの中身が空でないか | 中身が無い |
| SUMMARY が閉じているか / 入れ子でないか | 区切りが揃っていない・途中で切れている |

**モジュールの種類の正本**:

- 既存モジュールは**ブック側の種類が正本**。返答の `<種類>` が食い違っても
  ブックの種類のまま取り込み、画面 6 に常時表示の警告として何を読み替えたかを出す。
  返答の言い分でモジュールの型を変えることはしない。
- 新規モジュールは**標準モジュールのみ**受け付ける（§13.3）。
  `class` / `form` / `document` の新規追加は取り込みを断る。

失敗時は例外文・エラーコード・記号を画面に出さず、次にどうすればよいかを 1 文で
伝える（E-INTAKE-01）。ログには理由コードを残す。

## 7. データの流れとプロセス構成

### 7.1 全体像

```
使用者
 │ D&D / クリック
 ▼
WebView2 (HTML/JS)  ←― assets/ を https://macrostudio.local/ にマッピング
 │  window.chrome.webview.postMessage({id, action, params})
 ▼
C# ホスト (WPF, STA スレッド)
 │  03_MessageRouter が action を分岐
 ├─ 04_HostServices … ダイアログ / クリップボード読み書き / explorer / コードファイル / template / presets / ログ
 └─ 05〜08 エンジン … ブック読込・ビルド（メモリ内 byte[] 操作）
 │  PostWebMessageAsJson({id, status, data} または {event, data})
 ▼
WebView2 (JS)  … host-bridge.js が id で Promise 解決
```

- IPC は id 付き request/response + event push 方式。JSON は
  `System.Web.Script.Serialization.JavaScriptSerializer`（`MaxJsonLength = int.MaxValue`）。
- エンジン呼び出しはワーカースレッド（`Task.Run`）で実行し UI を固めない。
  応答は同じ id で返す。

### 7.2 IPC アクション一覧

| action | params | 応答 data | 備考 |
|---|---|---|---|
| `getAppInfo` | — | `{version, presets:[{file, content, error?}]}` | 起動時と画面 2 に入るたび JS が取得。`content` は presets/*.md の生テキスト（strict UTF-8）。読めなければ `content:""` と `error:"read"` を付けて一覧に残す。**ホストは H1 も節も解釈しない** |
| `pickBook` | — | `{path}` / `null` | OpenFileDialog（フィルタは §2.5） |
| `attachBook` | `{path}` | `{book:{path,name,ext,totalLines}, modules:[{name,type,typeLabel,ext,lineCount,code,attributes}]}` | code は先頭 Attribute ブロック除去済み。attributes は除去した元ヘッダ（ビルド時の再付与用に JS が保持）。失敗時 `{status:"error", code, message}` |
| `readPreset` | `{file}` | `{content}` | presets/ 内の `.md` のみ許可。押下のたびに読み直し、JS 側で解釈する |
| `readRequestTemplate` | — | `{content}` | `templates\request-template.txt` を生成のたびに strict UTF-8 で読む。失敗時 E-GEN-02 |
| `writeRequestFiles` | `{outputTimestamp, request, code}` | `{folderPath, requestPath, codePath}` | 実行フォルダを作り `request.md` と `source-code.md` を書く（§5.4）。ブックは attach 済み前提。失敗時 E-GEN-01 |
| `readClipboard` | — | `{text}` | 空なら `{text:""}` |

| `buildBook` | `{outputTimestamp, outputName, modules:[{name, code, isNew?}], diffHtml}` | `{outputPath, results:[{name, result, message}], diffPath?, diffError?}` | 出力は実行フォルダ内の `outputName`（ファイル名のみ・元の拡張子。不正なら E-BUILD-03）。既存 code は Attribute 再付与済み。新規は `isNew:true` と可視コードを渡し、C# 側で標準モジュールの Attribute を生成。HTML 出力失敗時もブックは成功。§5.4, §9 |
| `revealPath` | `{path}` | — | フォルダならそのフォルダを開き、ファイルなら explorer /select |
| `writeLog` | `{level, message}` | — | UI 側の要所ログ |

イベント push（C#→JS、id なし）: `bookDropped {path}`（D&D 受領時）。

### 7.3 クリップボード

- 取得は C# 側 `System.Windows.Clipboard.GetText()`（STA スレッド上で実行）。
  ブラウザの clipboard permission ダイアログを出さないための方式。
- 書き込みも C# 側 `Clipboard.SetText()`（同じ STA 経路）。書き込むのは
  依頼プロンプトだけで、コード本文をクリップボードへ入れる経路は作らない。
- Ctrl+V は JS の `paste` イベントで受け、`clipboardData.getData('text')` を使う
  （paste イベント内は許可不要）。ボタン経路とイベント経路で同じ正規化・
  同じ処理関数に合流させる。手動修正の編集欄やモジュール名入力欄など、
  編集可能なコントロールへの paste はブラウザ既定の動作に任せ、③の全体
  貼り付けハンドラでは奪わない。

### 7.4 ドラッグ＆ドロップ

WebView2 はクライアント領域全面を占める子ウィンドウを持つため、外部ドロップは
**まず WebView2 が受け取る**。`AllowExternalDrop = false` にすると WebView2 が
ドロップを拒否し、WPF 側の `Drop` にも届かない（実機で D&D が無反応だった原因）。
したがって次の構成で実装する。

1. **方式B（主経路）**: `AllowExternalDrop = true` を設定し、ページ側の
   `dragover`/`drop` で `chrome.webview.postMessageWithAdditionalObjects()` を使って
   `File` を host へ渡す。host は `e.AdditionalObjects` の `CoreWebView2File.Path`
   からフルパスを読み、`resolveDroppedFiles` の応答として JS へ返す。JS は通常の
   attach 経路（確認ダイアログ・警告表示を含む）でそのパスを添付する。
   （`postMessageWithAdditionalObjects` / `CoreWebView2File` は SDK 1.0.3856.49 対応）
2. **方式A（副経路）**: WPF 側 `PreviewDragOver`/`PreviewDrop` は残す。ページに届かない
   ドロップ（ウィンドウ枠など）を `DataFormats.FileDrop` から拾い、`bookDropped`
   イベントで JS へ渡す。
3. **方式C（常設の保険）**: 「ファイルを選ぶ」ボタン（OpenFileDialog）。

ドラッグ中は `body.is-file-drag` を付け、ドロップ先が分かるようにする。
MacroStudio と Explorer の整合性レベルが異なる場合（片方だけ昇格実行）は UIPI により
OS がドロップ自体を拒否する。この場合は方式C を使う。

### 7.5 ログ

- 出力先: `%LOCALAPPDATA%\MacroStudio\logs\macrostudio_<yyyyMMdd>.log`（追記、UTF-8）。
- 書式: `[HH:mm:ss] [LEVEL] message`。
- 記録する事象: 起動/終了、attach（パス・モジュール数）、コードファイル生成（パス）、
  貼り付け（モジュール名・行数のみ。**コード本文は記録しない**）、ビルド開始/結果、
  すべてのエラー（スタック含む）。

## 8. 貼り付けテキストの正規化

貼り付け時に次の規則を**この順で**機械的に適用する。これは §1.2 の「帳簿付け」であり、
ここに列挙した以外の加工をしてはならない。

1. 改行を CRLF に正規化する。
2. 行頭が ``` で始まる行（コードフェンス）を削除する
   （チャット AI のコピーボタンではなく手動範囲選択でコピーした場合の保険）。
3. **先頭から連続する** `Attribute VB_` 行（大文字小文字無視、行頭空白許容。
   間の空行は許容して読み飛ばす）を削除する（§6.4 と同じ「先頭ブロックのみ」規則。
   コード途中の Attribute 行には触れない）。
4. 先頭・末尾の空行を除去し、末尾に CRLF を 1 つ確保する。

正規化の結果はそのまま右ペイン・diff に出る（使用者から見て隠れた加工にしない）。
正規化後が空文字列なら貼り付け不成立（E-PASTE-01）。

ビルド直前の結合（JS 側）: 既存モジュールは
`保持していた Attribute ヘッダ + CRLF + 正規化済みテキスト` を最終コードとして渡す。
新規標準モジュールは可視コードと `isNew:true` を渡し、C# 側で `VB_Name` を生成する。

## 9. ビルド仕様（書き戻しエンジン）

### 9.1 手順

1. 元ブックを出力名（§5.4）でコピーする。**元ファイルには一切触れない**。
2. コピーから vbaProject.bin（zip エントリ）を取り出し、OLE2 として読み込み、
   **全エントリの論理情報と全ストリーム内容をメモリに展開**する。
3. 書き戻し対象モジュール（取り込み済みかつ変更あり）ごとに、新しいストリーム内容を作る:
   - 既存モジュールは、最終コード（Attribute 付き）をプロジェクトのコードページで
     encode → MS-OVBA 圧縮する。モジュールストリームの先頭
     `[0, SourceOffset)`（PerformanceCache 部）は
     そのまま温存し、`SourceOffset` 以降を新しい圧縮データに差し替える。
     **SourceOffset は dir の MODULEOFFSET を正本**とし、書き戻し対象ストリームは
     **dir の MODULESTREAMNAME で対応付ける**。
   - 新規標準モジュールは `Attribute VB_Name` と可視コードの全文を圧縮し、
     PerformanceCache なし（`MODULEOFFSET=0`）の新規ストリームにする。
     dir の `PROJECTMODULES` と MODULE レコード、PROJECT の `Module=` 行、
     PROJECTwm の NAMEMAP を同じ順序で追加する。
4. **OLE2 複合ドキュメントを丸ごと再構築する（§9.2。唯一の書き込み経路）**:
   全エントリ（差し替えたストリームと新規モジュールストリームを含む）を
   新しいコンテナとして直列化する。
5. 再構築した vbaProject.bin をコピー先ブックに書き戻す（zip の該当エントリを
   Update モードで書き換え）。
6. **検証（必須手順）**: コピー先ブックをエンジンで読み直し、次の 3 点を確認する。
   - (a) 書き戻した全モジュールの展開後テキストが、渡した最終コードと一致
     （CRLF 正規化後の完全一致）
   - (b) 新規追加時に更新する dir / PROJECT / PROJECTwm と新規ストリームを除き、
     **それ以外の全ストリームが元の内容と byte 単位で一致**
   - (c) ストレージ/ストリームの木構造・名前・種別・CLSID・state bits が
     維持されている
7. 1 つでも失敗（検証・I/O）したら**出力ファイルを削除**し、モジュール別の結果を
   返す（**all-or-nothing**。中途半端に直ったブックを現場に残さない）。

### 9.2 全面再構築方式

**なぜ全面再構築か**: 既存セクタチェーンへ in-place で書き込む方式
（+ パディング + リロケートの 3 段配置規則）は、本ツールの用途では成立しない。
実測では、典型的な改修として 1 行追加しただけで、検証した全モジュール
（18/18。すべて mini ストリーム、スラック 0〜41B に対し圧縮後の増分 55〜75B）が
in-place 不能だった。「コードが増える」のが常態である以上、
**全面再構築を唯一の書き込み経路**とする。

**方式**: コンテナ（MS-CFB）水準の再構築。

- **保持する論理情報**（元から機械的に移送）: ストレージ/ストリームの木構造（親子）、
  名前、種別、CLSID、state bits、作成/更新時刻、全ストリーム内容。
  モジュールストリーム以外のストリーム（`_VBA_PROJECT` / `dir` / `__SRP_*` /
  `PROJECT` / `PROJECTwm` 等）は、既存モジュールだけの変更では
  **内容を解釈せず、不透明な byte 列としてコピー**する。新規追加時だけ、
  dir / PROJECT / PROJECTwm に規定のレコードを追加する。
- **毎回新規に決めるもの**（物理配置。MS-CFB 上、意味を持たない）: セクタ番号、
  チェーン順序、空きセクタ、FAT / DIFAT / miniFAT の中身。
- mini / 通常ストリームの所属は、再構築時に各ストリームのサイズ（cutoff 4096）から
  自然に決まる。**パディングは不要**。
- ディレクトリの兄弟赤黒木は MS-CFB の名前順（長さ → 大文字化比較）で構築する。
- 出力は v3（512B セクタ）で直列化する。v4（4096B セクタ）の入力は実務上ほぼ無い
  想定で、遭遇した場合は明示エラーにする（未検証事項として記録）。
- 出力ファイルのバイト配置は元と変わる（空きセクタが落ちるため通常は小さくなる）が、
  意味的な差はない。
- 署名: VBA プロジェクト署名は vbaProject.bin の外の別パート
  （`xl/vbaProjectSignature.bin` 等）にあり、モジュールを書き換えた時点でどの書き込み
  方式でも無効になる。再構築固有の不利ではない。v1 は署名パートに触れない。

**品質保証（必須。すべて満たすまでリリースしない）**:

1. **ラウンドトリップ試験**: 無変更で再構築 → 全ストリーム byte 一致・木構造等の
   論理情報一致（開発時の常設テスト。毎ビルドが同じ経路を通るため、この試験が
   本番経路そのものを検証する）。
2. **ビルド後の読み直し検証**（§9.1-6。全ストリーム対象）。
3. **Excel 実機確認**（再構築した出力を Excel で開き、マクロ動作を確認する。
   リリース前の手動確認項目）。

### 9.3 書き戻しが変更しないもの

- 既存モジュールの PerformanceCache（各モジュールストリームの先頭部）、
  `_VBA_PROJECT` / `__SRP_*` 等の他ストリーム: **内容を一切変更しない**
  （再構築で物理配置は変わるが、内容は byte 単位で維持され、§9.1-6(b) で検証される）。
  既存ソースの差し替えと新規標準モジュールの追加だけを行い、再コンパイルは Excel 側に任せる。
- dir / PROJECT / PROJECTwm は新規追加時だけ必要なレコードを追記し、
  それ以外の既存 byte 列を維持する。
- zip 内の vbaProject.bin 以外のエントリ（シートデータ等）: 触れない。

### 9.4 モジュール別結果コード

| result | 意味 | all-or-nothing 後の扱い |
|---|---|---|
| `written` | 書き戻し・検証 OK | 成功時のみ |
| `verify_failed` | 読み直し検証で不一致 | 全体失敗（出力破棄） |
| `io_error` | コピー/zip 書き戻し失敗 | 全体失敗 |
| `skipped_no_change` | 変更なしのため書き戻し対象外 | 情報表示のみ |

再構築処理そのものの内部エラーは、モジュール別ではなくビルド全体のエラーとして
扱う（E-BUILD-01。出力は残さない）。

## 10. 状態遷移

### 10.1 画面の遷移

```
[起動] → 0 読み込み → 1 確認 → 2 目的 → 3 依頼文
   → 4 受け渡し（実行フォルダを作成） → 5 取り込み → 6 確認
   → 7 出力名 → 8 ビルド中 → 9 完了
```

- 進めるのは［次へ］だけで、条件は §4 の表が全量。分岐は無い。
- ［戻る］は通った経路を逆にたどる（履歴）。8 だけは戻れない。
- 6 の「取り込みをやめる」は、取り込んだ変更をすべて破棄して 5 へ戻す。
- 0 でブックを読み込み直すと全状態をリセットする。取り込み済みが 1 件でもあれば
  確認ダイアログを挟む（トップバーの［最初から］も同じ扱い）。
- 画面を往復しても、依頼文・依頼 ID・取り込み済みコード・出力名は保持する。

### 10.2 モジュールの状態

「全部未取り込みで始めて、返答に入っていたものが書き戻される」を基本とし、
次の状態を持つ。取り込みは返答パッケージ単位なので、1 回の取り込みで
複数のモジュールが同時に移る。

```
未取り込み ──返答パッケージ──▶ 変更あり（書き戻し対象）
    ▲                              │
    └────［戻る］→ 取り込み直し ────┘
返ってきた内容が現在と同一の場合は「変更なし」（書き戻し対象にならない）
新規モジュール ──▶ 変更あり（新規）──取り込み直し──▶ 一覧から削除
手動修正で内容を変えても、そのモジュールは書き戻し対象のまま
```

| 状態 | 一覧の表示 | 誰が決めるか |
|---|---|---|
| 未取り込み | 灰ドット + 「そのまま」 | 初期状態（返答に入っていなかった） |
| 変更あり | 青ドット + 「+N 行」 | **返答に入っていた事実**によって自動 |
| 変更なし | 灰ドット + 「変更なし」 | 返ってきた内容が現在コードと同一のとき自動 |

- 状態は表示専用で、ここから直接ビルドを起動する操作は持たない。
- モジュールごとの採否・除外・貼り直しは持たない。単位は常にパッケージ 1 つ。
- ツールがチャット AI の返答から対象モジュールを推定することは**しない**（§1.2）。
  返答が自分で名乗ったモジュールだけを、依頼 ID の検証を通してから取り込む。
  何を渡すか（どの返答を取り込むか）を決めるのは常に人である。

## 11. 画面の案内文

レクチャー欄（ラベル付きの折り畳みパネル）は持たない。案内は次の 3 か所だけに置き、
いずれも普通の文章として書く。

| 置き場所 | 内容 | 実装 |
|---|---|---|
| 画面見出し | 手順番号（例: 手順 2 · 3/4）と、その画面ですることの一文 | `screens.js` の `title` |
| 画面見出しの右 | いま扱っている対象（ブック名、モジュール名、件数など） | `screens.js` の `meta` |
| 中央の 1 行（`.task-intro`） | この画面で操作する内容の短い説明 | 各画面ビルダー |
| 固定操作領域の左 | 次にすること 1 つだけ | `screens.js` の `context` |
| 開閉領域のラベル | 開くと何が出るか（「依頼文を確認・編集」など） | `createDisclosure` の label |

書き方の決まり:

- 初めて使う人へ、その場で何をすればよいかだけを伝える。
- 開閉領域のラベルは中身を名乗る。「詳細設定」「オプション」のような
  何が出るか分からない名前は使わない（§4.1）。
- 取り込みに失敗したときは、例外文・エラーコード・記号を画面に出さず、
  次にどうすればよいかだけを 1 文で書く。
- 開発過程や設計理由が透ける説明（「本番版 Diff」「◯◯と同じ内容」など）は書かない。
- エラーはトーストで出し、コードは技術的な確認が要る場合だけ添える（§12）。
- 絵文字は使わず、アイコンは一貫した線画 SVG に限る。

## 13. 検討論点への回答

### 13.1 diff 表示: Monaco は使わない → 自前 diff 描画の設計

Monaco Editor は**使わない**。diff は MacroStudio 自身の JS 実装とする。

| 部位 | 実装先 |
|---|---|
| 貪欲法の行 diff（先読み窓 100 行、changed ペアリング） | `assets/js/diff.js` |
| インライン表の構造と配色（equal/added/removed、2 本の行番号列、マーカー列、両テーマ） | `assets/js/diff-view.js` + `assets/css/diff.css` |
| ビルド後の自己完結 HTML（左にモジュールツリー、右に全変更モジュールのインライン比較） | `assets/js/diff-report.js`（計算は `diff.js` を直接利用） |

比較結果（equal / changed / added / removed のペア行）を表示行へ開く規則は
`diff-view.js` の `expandRow` に 1 か所だけ置き、HTML レポート側も同じ規則で書く。
changed の 1 行は「削除行 → 追加行」の 2 行になる。

追加設計（③ の要件への適合）:

- diff は**貼り付け前はボタンのみ、貼り付け後はメイン画面いっぱいのインライン表**になる。
  diff テーブル自体は読み取り専用で、エディタエンジンは不要。読み取り専用の
  「エディタの見た目」（等幅フォント・行番号・テーマ別配色）を diff テーブルで実現する。
  手動修正（§3.4）は plain textarea による独立した編集画面で行い、
  反映時に通常の貼り付けと同じ正規化・diff 計算へ合流させる。
- シンタックスハイライト: 軽量な行単位トークナイザ（コメント / 文字列 / キーワード /
  数値の 4 分類程度）を `assets/js/vba-highlight.js` として自前実装する。
  equal / added / removed の全行に適用し、diff 背景色と併用する。
- 行内（単語レベル）の変更強調: 変更行の共通接頭辞・接尾辞を除いた差分範囲を
  濃い背景で示し、空白は中黒、タブは矢印で可視化する。削除側・追加側の両方に付ける。
- 長い行は横スクロールを既定とし、ツールバーの［折り返す］で切り替える。
- 「変更箇所のみ表示」トグルは常時表示し、200 行超のモジュールでは既定 ON、
  200 行以下では既定 OFF とする。折り畳んだ区間は省略行数を示し、クリックで展開できる。
- ［前の変更］［次の変更］で変更ブロック間を移動できる。

### 13.2 状態バッジは誰が付けるか

§10.2 のとおり「全部グレー → 貼ったものが取り込み済み」を基本とし、
「事実由来のバッジは自動、意図由来のバッジ（対象外）だけ手動」という整理を加えた。
自動バッジはすべて「使用者がした操作」または「ビルドの結果」という**ツール内で
確定している事実**から導かれ、チャット AI の返答解釈を一切必要としない。

### 13.3 新規モジュール追加を v1 に含めるか（結論: 標準モジュールのみ含める）

- 共通処理を既存モジュールへ重複して置かず、新しい標準モジュールへ分離できる。
- 名前と種類は返答パッケージの区切り行が名乗る（§6.5）。区切りの検証を通った
  ものだけを取り込み、コード本文から名前や種類を推測することはしない。
- OLE2 の新規ストリーム、dir の MODULE レコード、PROJECT の `Module=` 行、
  PROJECTwm の NAMEMAP を一括して追加し、§9.1 の読み直し検証を通す。
- **新規追加は標準モジュールのみ**。writer は `Module=` / dir type 0x0021 /
  `VB_Name` だけを生成し、読み直し検証も追加物を Standard として確認する。
  返答が `class` / `form` / `document` の新規追加を含む場合は取り込みを断り、
  ひな形の出力指示にも「新しく増やすモジュールは標準モジュールだけ」と明記する。
- **既存モジュールの改修は種類を問わない**。クラスモジュールも含めて改修でき、
  抽出時の属性ヘッダー（`VB_PredeclaredId` / `VB_Exposed` など）を再結合して
  書き戻し、読み直し検証で種類を問わずコード一致を確認する
  （`tests\test-monthly-report-roundtrip.ps1` と `tests\test-class-roundtrip.ps1`）。
- 削除・名前変更は対象外。

### 13.4 利用者の習熟度に応じたモード分けを v1 に含めるか（結論: 含めない）

- 1 画面 1 判断の一本道が、そのまま不慣れな利用者向けの体験になっている。
  慣れた利用者が欲しがる自由度（依頼文の自由編集、ひな形の差し替え、出力名の変更、
  取り込みの繰り返し）は、**モードを分けなくても同じ流れの中にある**。
- モード切替 UI は「自分はどちらか」という迷いどころを増やし、§1.3 の原則に反する。
  文言・テストの二重管理コストも v1 の価値に見合わない。
- 将来、上級者向け機能（一括処理・解析系など）が実際に必要になったら、`settings.json` の
  フラグで**画面に切替を出さずに**追加する方式を推奨（付録 A）。

## 14. v1 スコープ外（明示）

- モジュールの削除・リネーム、標準モジュール以外の新規追加（§13.3）
- Attribute 行の変更（§6.4）、UserForm のコントロール（レイアウト・.frx）編集
- チャット AI 返答の自動解釈・自動振り分け
- 複数ブックの一括処理、モード分け（§13.4）
- VBA プロジェクトのパスワード保護の解除（保護があっても改修自体は可能な見込み。§2.5）
- ツールからの Excel 起動・マクロ実行（動作確認は使用者が Excel で行う）
- コード本文のクリップボード受け渡し（コードは常に添付ファイルで渡す。
  クリップボードへ入れるのは依頼文だけ）

## 15. 既知の制限・未検証事項

v1 時点で「動くと確認できていること」と「まだ確認できていないこと」を分けて記す。
不具合の一覧ではなく、どこまで検証済みかの範囲表である。

### 15.1 実機で確認済み

- `.xlsm` の抽出・書き戻し・Excel での再オープンとマクロ実行。
- 無変更での再構築による全ストリームの byte 一致（ラウンドトリップ試験）。
- サイズの増減（+50% / +500% / 大幅削減 / mini↔通常ストリーム境界の跨ぎ）。
- DIFAT 継続（ヘッダの 109 参照を超える FAT）を持つ合成 fixture の読み・再構築。
- 複数モジュールの同時変更と all-or-nothing の失敗時挙動。
- 新規標準モジュールの追加、dir / PROJECT / PROJECTwm / 新規ストリームの再読検証、
  Excel での再オープンと追加マクロの実行。

### 15.2 未検証・限定的な範囲

1. **`.xlsb`**: 実ファイルの fixture を用意できていないため、best-effort 経路は
   実機未検証。解析に失敗した場合は E-ATTACH-05 の明示エラーになる。
2. **パスワード保護された VBA プロジェクト**: 仕様上は影響を受けない見込み（§2.5）だが、
   実ファイルでの確認は未実施。
3. **`.xlam`**: 合成 ZIP による経路の試験であり、Excel が実際に生成した fixture では
   検証していない。
4. **v4（4096B セクタ）の CFB 入力**: 読み取りは可能だが、書き出しは v3 のみ。
   v4 入力の再構築要求は明示エラーになる。実ファイルでの遭遇例は未確認。
5. **起動時ネイティブエラーのログ副作用**: WebView2 ランタイム不在時の MessageBox 経路は
   実機確認済み。その後に追加した起動エラーの best-effort ログ出力は、コンパイル確認
   のみで、ランタイム不在を再現しての実測はしていない。
6. **配布形態の E2E**: 別ディレクトリへ配置した状態からの `launch.vbs` 起動・ウィンドウ表示・
   コンソール非表示・ログ出力・終了は実プロセスで確認済み。ただしステップ ①〜④ の
   通し確認は、同じ配置物から起動した検証用 harness で行っており、先に起動した
   実プロセスを UI 自動操作したものではない。

### 15.3 実装済みだが未着手の整理

- 実装完了後のリファクタリングは未実施。動作と試験結果を優先し、構造の整理は
  後回しにしている。
